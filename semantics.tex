\section{Semantics}
\label{sec:semantics}

This paper's semantics of Skia
  consists of three components.
The bottom-most layer is an abstract model of
  images, shapes, blends, and filters defined in terms
  of abstract types \Point and \Color,
  which can be instantiated to model
  as much of the actual Skia API as necessary.
The middle layer is functional operations
  \texttt{Draw} and \texttt{BlendLayer}
  and an abstract type \textsf{Paint},
  which denote to our abstract model.
The top layer is an imperative language, \muskia,
  whose operational semantics provides a model of Skia.
This section describes all three layers
  and then examines \fillin{4} rewrite rules
  proven valid using the semantics.

\subsection{Abstract Model}
\label{subsec:abstractmodel}

\begin{figure}
  \centering
  \begin{tabular}{S S S}
    Image  & : \; Point $\to$ Color & \textrm{\textit{e.g.}}\; {\sffamily
                                      Solid(Color), LinearGradient($\ldots$),
                                      $\ldots$} \\[4pt]
    Shape  & : \; Point $\to$ Bool & \textrm{\textit{e.g.}}\; {\sffamily
                                     Rect($\ldots$), RRect($\ldots$),
                                     Path($\ldots$), Text($\ldots$)} \\[4pt]
    Blend  & : \; Color $\times$ Color $\to$ Color & \textrm{\textit{e.g.}}\;
                                                     {\sffamily SrcOut, DstIn,
                                                     $\ldots$} \\[4pt]
    Filter & : \; Color $\to$ Color & \textrm{\textit{e.g.}}\; {\sffamily Id,
                                      Luma, $\ldots$}
  \end{tabular}
  \caption{%
    Our abstract model of \Image{}s
      and \Shape{}s is built from
      abstract types \Point{}s and \Color{}s.
    We also include the various instantiations of the types in model we us in
      our formalization.
  }
  \label{fig:model}
\end{figure}

Traditional programming language semantics
  typically do not have to define their abstract model,
  since it is typically based on commonly-known types
  such as pairs, functions, and integers.
In the graphics domain, the core types
  are not so well established,
  so the abstract model must be explicitly defined.
The abstract model of our semantics
  is shown in \Cref{fig:model};
  it is based around two core abstract types,
  \Point and \Color.
The \Point and \Color types
  are then used to define the key types in our abstract model.
An \Image is defined
  as a \Color for every \Point
  while \Shape{}s are defined
  as predicates on \Point{}s.
Equivalence of two \Image{}s is defined
  as assigning the same \Color to each \Point.
Additionally, since a major focus of this semantics
  is reasoning about color blending and filtration,
  types for \Blend{}s and \Filter{}s are defined
  as binary and unary operators on colors.

This abstract model hides substantial complexity
  in the actual implementation.%
\footnote{
In the same way that a traditional programming language semantics
  might hide the complexity of actually storing closures on the heap.
}
The actual Skia implementation
  defines \Point to be a pair of 32-bit signed integers
  and \Color to be a 32-bit unsigned integer
  interpreted as ARGB pre-multiplied byte-sized color,%
\footnote{
``ARGB'' gives the in-memory byte order
  of the alpha, red, green, and blue components of a color.
The interpretation of these bytes as an unsigned 32-bit integer
  will depend on the endianness of the platform itself.
The colors are premultiplied, meaning
  that a color with an alpha value of $\alpha$
  will have its red, green, and blue components
  range from $0$ to $\alpha$;
  this form makes for somewhat more efficient computation.
}
  and operations on points and colors
  must thus be anti-aliased and rounded.
The exact anti-aliasing and rounding behavior
  is not guaranteed by Skia
  and is also exceptionally complex,
  including hardware dependence in some back-ends;
  the abstract model allows our semantics
  to ignore these details.
The equivalences proved are thus
  \emph{up to} anti-aliasing and rounding details
  (and also assume away issues like coordinate overflow).

Matching the abstract model to Skia
  would require actually defining
  the vast array of \Image{}s
  (solid color fills, gradients, image files),
  \Shape{}s (rectangles, paths, text outlines),
  \Blend{}s (roughly two dozen),
  and \Filter{}s (in fact, these can even be defined
  by shader programs in a custom SkSL shader language).
Defining these objects and their equivalences
  would be a complex undertaking,
  especially given the pace of change in Skia itself.
Luckily, the compiler described in \Cref{sec:compiler}
  does rather superficial reasoning over these objects
  and only special-cases a handful of them.
Our Lean formalization only defines those special cases.
The abstract model nonetheless allows for extensibility;
  for example, this section does not discuss opacity,
  but our Lean formalization does include it.
This extension does not require any changes to the abstract model,
  and only some tweaks in the denotational semantics defined in the remainder of
  this section.

\subsection{Skia as Layers}
\label{subsec:sem-layers}

\begin{figure}
  \centering

      Paint ::= \\

    \end{tabular}

  \end{subfigure}
  \hfill

    \centering
    \begin{tabular}{ScS}
      Command ::= \\
      | Draw($g$: Shape, $p$: Paint) \\
      | Clip(\textit{cl}: Shape) \\
      | Save(); $c$; Restore() \\
      | SaveLayer($p$: Paint); $c$; Restore() \\
      | $c$; $c$
    \end{tabular}
    \caption{}
    \label{fig:muskia}
  \end{subfigure}
  \caption{In \Cref{fig:layerlang} we show the grammar of the \Layer
    language that constrains the order of operations over our abstract model
    described in \Cref{subsec:abstractmodel}. Note how all the \Layer terms are
    made up of the the primitive types defined in the abstract model. In
    \Cref{fig:muskia} we show the grammar of the \muskia language. \muskia uses

    Skia API, we define \Save/\Restore and \SaveLayer/\Restore pairs as structured constructs
    for convenience.}
\end{figure}

Skia does not permit
  arbitrary drawing and blending operations;
  instead, these always happen in a prescribed order.
We thus introduce the language of \textsf{Layers},
  shown in \Cref{fig:layerlang},
  which defines the core \texttt{Draw} and \texttt{BlendLayer} operations
  in Skia.
We focus on these two operations specifically
  because they are the core target of the optimizing compiler
  described in \Cref{sec:compiler}.
The \layer constructors can be defined in terms of the abstract model,
  as shown in \Cref{fig:denote}.

\begin{figure}
  \begin{align*}
    \denote{\Empty()}(\textsf{pt})
    &= \Transparent\\[2pt]
    \denote{\BlendLayer(\ell_\textsf{bot}, \ell_\textsf{bot}, p)}(\mathsf{pt})
    &= \mathsf{blend_\mathrm{p}}\left(\denote{\mathsf{\ell_{bot}}}(\mathsf{pt}),\;
        \textsf{filter\textsubscript{\textrm{\textit{p}}}}\left(\denote{\mathsf{\ell_{top}}}(\mathsf{pt})\right)
      \right) \\[2pt]
    \denote{\Draw(\ell, s, p, c)}(\mathsf{pt})
    &= \mathsf{blend_\mathrm{p}}\left(\denote{\ell(\mathsf{pt})},\;
      \textsf{filter\textsubscript{\textrm{\textit{p}}}}\left(
       \left\{
       \begin{array}{ll}
         \mathsf{fill_\mathrm{p}}(\mathsf{pt}) & \mathsf{pt} \in s \\
         \Transparent & \textsf{otherwise}
       \end{array}
       \right\}
       \right)\right)\\
  \end{align*}
  \caption{Denotational semantics for \Layer terms.}
  \label{fig:denote}
\end{figure}

Skia has two core operations:
  drawing a shape onto an image,
  and blending two images (representing two layers) into one.
Each operation is parameterized by a \textsf{Paint} object,
  which indicates the current blend mode,
  the fill type, and so on;
  drawing also requires the clip region from the canvas state.
The signatures for each operation are defined
  in \Cref{fig:layer} as constructors of
  a \textsf{Layer} type.
Equivalence of two \textsf{Layer} terms
  is defined by equivalence of their denotations to \Image{}s.

The operations can be denoted to the abstract model,
  as shown in \Cref{fig:denote}.
\textsf{Empty} has a straightforward denotation
  to an all-\textsf{Transparent} image.
\textsf{BlendLayer} is likewise straightforward,
  applying a blend operator, determined by the paint $p$,
  point-wise on the two layers being blended.
\textsf{Draw} is most complex.
Conceptually, it first performs clipping,
  constructing the intersection $s \cap c$
  of the drawn shape and the clip state;
  then it performs filling,
  computing the fill color for each point in the shape;
  and finally it performs blending
  on the original color and computed fill for each point.
The blend is performed
  even for points outside $s \cap c$;
  this is critical for, for example, \textsf{DstIn} blending.
Note that the equalities over denotations are compositional.
That is, if we know that $\denote{l} = \denote{l}$,
  then $\denote{m} = \denote{m[l/l']}$.
The fact that denotations are composable means
  we can use equalities over denotations as rewrites,
  enabling us to actually use our semantics
  to verify optimizations.

\subsection{\muskia}
\label{subsec:muskia}

\muskia is a simplified version of the Skia API.
A \muskia program consists
  of a sequence of commands
  whose syntax is defined in \Cref{fig:muskia}.
\muskia includes the critical features
  described in \Cref{sec:skia},
  such as the \textsf{Draw} command for drawing,
  the \textsf{Clip} command for manipulating the clip state,
  and the \textsf{Save}, \textsf{SaveLayer}, and \textsf{Restore}
  stack manipulation commands,
\muskia diverges from the full Skia API
  in two main ways.
First, the syntax definition is more regular
  to eliminate unimportant special cases:
  \textsf{Save}, \textsf{SaveLayer}, and \textsf{Restore}
  must be properly bracketed,
  and the \texttt{Draw} and \texttt{Clip} commands
  take arbitrary \textsf{Geometry}s,
Second, only a small fraction of the API is modeled.
Nonetheless,
  extending \muskia to cover more of the API is straightforward,
  and our Lean formalization includes additional features
  such as opacity, styles, and transforms.

\muskia programs manipulate a state $\Sigma$:
\[
\Sigma:\textsf{List[Layer]} \times \textsf{List[Geometry]}
\]
The first list in $\Sigma$ is the stack of layers
  manipulated by \textsf{SaveLayer},
  while the second list is the stack of canvas states
  manipulated by \textsf{Save}.
In this paper, the canvas state is a single \textsf{Geometry}
  because the only canvas operation is \textsf{Clip},
  but in our Lean formalization the canvas state
  includes additional fields.
As is standard, we treat the head of the list
  as the top of the stack.
The initial state is
  $\langle [ \texttt{Empty()} ], [ \mathcal{U} ] \rangle$,
  an empty layer and the full clip state,
  each as single-element stacks.
A \muskia program then performs
  a sequence of steps  $(c, \Sigma) \longmapsto \Sigma'$,
  after which the final state
  consists of a single layer $L$,
  which is the output image,
  and some clip state, which is discarded.

We now describe the core steps
  in the operational semantics.
The simplest is the \textsf{Draw} command,
  which modifies the top \textsf{Layer}:
\begin{mathpar}
  \inferrule
  { }
  {
    \langle
    \Draw(s, p),
    \langle \ell :: L, c :: C \rangle
    \rangle
    \;\longmapsto\;
    \langle \Draw(\ell, s, p) :: L, c :: C \rangle
  }
\end{mathpar}
\noindent
Note that the \textsf{Draw} operation on the top \textsf{Layer}
  includes both the \textsf{Geometry} and \textsf{Paint}
  from the \textsf{Draw} command
  as well as the current clip from the canvas state:

The \textsf{Clip} command likewise modifies
  the top canvas state, intersecting it
  with the new clip geometry:
\begin{mathpar}
  \inferrule
  { }
  {
    \langle
    \Clip(c'),
    \langle L, c :: C\rangle
    \rangle
    \;\longmapsto\;
    \langle L, c \cap c' :: C \rangle
  }
\end{mathpar}
\noindent
Note that the full Skia API includes a
  \texttt{SkClipOp} parameter
  that allows instead taking the difference
  between the current and new clip;
  this paper does not show that (straightforward) extension
  but our Lean formalization does include it.

The \textsf{Save} command
  duplicates the top canvas state.
Then, when its matching \textsf{Restore} is reached,
  that top canvas state is discarded:
\begin{mathpar}
  \inferrule
  {
    \langle
    \mathit{cmd},
    \langle L, c :: c :: C \rangle
    \rangle
    \;\longmapsto\;
    \langle L', c' :: c :: C \rangle
  }
  {
    \langle
    \Save(); \mathit{cmd}; \Restore(),
    \langle L, c :: C\rangle
    \rangle
    \;\longmapsto\;
    \langle L', c :: C \rangle
  }
\end{mathpar}
\noindent
Note that it does not make
  any changes to the layer state.

The \textsf{SaveLayer} command, meanwhile,
  allocates a new, empty layer
  for the top of the layer stack and,
  when the \textsf{Restore} command is reached,
  blends that new layer with the one below:
\begin{mathpar}
  \inferrule
  {
    \langle
    \mathit{cmd},
    \langle \Empty() :: ell :: L, c :: c :: C \rangle \rangle
    \;\longmapsto\;
    \langle \ell' :: \ell :: L, c' :: c :: C \rangle
  }
  {
    \langle
    \SaveLayer(p); \mathit{cmd}; \Restore(),
    \langle \ell :: L, c :: C\rangle
    \rangle
    \;\longmapsto\;
    \langle \BlendLayer(\ell, \ell', p) :: L, c :: C \rangle
  }
\end{mathpar}
\noindent
The inference rule for sequential composition is straightforward
  and, along with various extensions to \muskia,
  is given in our Lean formalization,
  which we intend to submit as an artifact.

The \muskia semantics is deterministic,
  and programs never get stuck.

\subsection{Lean Formalization}

We have mechanized the abstract model, \Layer terms, and \muskia and their
  respective semantics in the Lean4 interactive theorem prover~\cite{lean4}.
Of note in our mechanization,
  we have also concretized both ofthe main types--\Point and \Color--of our abstract model.
We represent \Point as a 2-tuple of integers,
  while we represent \Color as a premultiple-ARGB color, \emph{i.e.} we
  represent \Color as 4 intervals, one for each channel, and the alpha channel
  is bounded form 0 to 1, while the color channels are bounded from 0 to alpha.
While the concretization of \Point does not make the mechanization any more
  interesting,
  the concretization of \Color does.
We are able to define blend modes as real valued functions, and prove
  indentities about them, which we use to prove our rewrites in
  \Cref{sec:rewrites}.

We also mechanize certain aspects of the Skia API that we do not discuss in the
  semantics or use to prove the rewrites.
Specifically,
  we formalize the notion of ``style''-- whether a geometry is to be filled, or
  only its boundaries-- and that of ``opacity'' both only require extensions to
  the denotational semantics of \Layer terms.
We also omit the notion of affine transformations in Skia from the smeantics we
  presented here.
Like clipping, Skia maintains a stack of the current ``transform'' of the layer,
  which describes the affine transformation under which the current geometry is
  to be drawn.
Supporting this is easy; we only have extend the operational semantics of
  \muskia to accomadate affine transformations.
Just like how we get rid of clip state while transforming \muskia terms into
  \Layer terms, we can do the same with affine transformations.

There are also some parts of Skia's API we do not describe here or mechanize,
  mainly mask filters and image filters.
These have no consequence to the rewrite rules,
  and we also show later on in \Cref{subsec:rq1} that our rewrite rules function on
  Skia programs that cannot be represented by \muskia.
