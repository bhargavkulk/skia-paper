This paper's semantics of Skia
  consists of three components~\Cref{fig:diagram}.
The bottom-most layer is an abstract model of
  images, shapes, blends, and filters defined in terms
  of abstract types \textsf{Point} and \textsf{Color},
  which can be instantiated to model
  as much of the actual Skia API as necessary.
The middle layer is functional operations
  \texttt{Draw} and \texttt{BlendLayer}
  and an abstract type \textsf{Paint},
  which denote to our abstract model.
The top layer is an imperative language, \muskia,
  whose operational semantics provides a model of Skia.
This section describes all three layers
  and then examines \fillin{??? Count them} rewrite rules
  proven valid using the semantics.

\subsection{Abstract Model}

Traditional programming language semantics
  typically do not have to define their abstract model,
  since it is typically based on commonly-known types
  such as pairs, functions, and integers.
In the graphics domain, the core types
  are not so well established,
  so the abstract model must be explicitly defined.
The abstract model of our semantics
  is shown in \Cref{fig:model};
  it is based around two core abstract types,
  \textsf{Point} and \textsf{Color}.
The \textsf{Point} and \textsf{Color} types
  are then used to define the key types in Skia.
An \textsf{Image} is defined
  as a \textsf{Color} for every \textsf{Point}
  while \textsf{Shape}s are defined
  as predicates on \textsf{Point}s.
Equivalence of two \textsf{Image}s is defined
  as assigning the same \textsf{Color} to each \textsf{Point}.
Additionally, since a major focus of this semantics
  is reasoning about color blending and filtration,
  types for \textsf{Blend}s and \textsf{Filter}s are defined
  as binary and unary operators on colors.

This abstract model hides substantial complexity
  in the actual implementation.%
\footnote{
In the same way that a traditional programming language semantics
  might hide the complexity of actually storing closures on the heap.
}
The actual Skia implementation
  defines \textsf{Point} to be a pair of 32-bit signed integers
  and \textsf{Color} to be a 32-bit unsigned integer
  interpreted as ARGB pre-multiplied byte-sized color,%
\footnote{
``ARGB'' gives the in-memory byte order
  of the alpha, red, green, and blue components of a color.
The interpretation of these bytes as an unsigned 32-bit integer
  will depend on the endianness of the platform itself.
The colors are premultiplied, meaning
  that a color with an alpha value of $\alpha$
  will have its red, green, and blue components
  range from $0$ to $\alpha$;
  this form makes for somewhat more efficient computation.
}
  and operations on points and colors
  must thus be anti-aliased and rounded.
The exact anti-aliasing and rounding behavior
  is not guaranteed by Skia
  and is also exceptionally complex,
  including hardware dependence in some back-ends;
  the abstract model allows our semantics
  to ignore these details.
The equivalences proved are thus
  \emph{up to} anti-aliasing and rounding details
  (and also assume away issues like coordinate overflow).

Matching the abstract model to Skia
  would require actually defining
  the vast array of \textsf{Image}s
  (solid color fills, gradients, image files),
  \textsf{Shape}s (rectangles, paths, text outlines),
  \textsf{Blend}s (roughly two dozen),
  and \textsf{Filter}s (in fact, these can be defined
  by shader programs in a custom SkSL shader language).
Defining these objects and their equivalences
  would be a complex undertaking,
  especially given the pace of change in Skia itself.
Luckily, the compiler described in \Cref{sec:compiler}
  does rather superficial reasoning over these objects
  and only special-cases a handful of them.
Our Lean formalization only defines those special cases.
The abstract model nonetheless allows for extensibility;
  for example, this section does not discuss opacity,
  but our Lean formalization does include it.
This extension does not require any changes to the abstract model,
  only the addition of specific color and blend operators,
  and thus re-uses the denotational and operations semantics
  defined in the remainder of this section.

\subsection{Skia as Layers}
\label{subsec:sem-layers}

Skia does not permit
  arbitrary drawing and blending operations;
  instead, these always happen in a prescribed order.
We thus introduce the language of \textsf{Layers},
  shown in \Cref{fig:layer},
  which defines the core \texttt{Draw} and \texttt{BlendLayer} operations
  in Skia.
We focus on these two operations specifically
  because they are the core target of the optimizing compiler
  described in \Cref{sec:optimize}.
The \layer constructors can be defined in terms of the abstract model,
  as shown in \Cref{fig:denote}.

\begin{figure}
  \begin{align*}
    \denote{\texttt{Empty()}}(\textsf{pt})
    &= \mathsf{Transparent}\\[2pt]
    \denote{\texttt{BlendLayer(l\textsubscript{bot}, l\textsubscript{top},
    p)}}(\mathsf{pt})
    &= \mathtt{blend_p}\left(\denote{\mathtt{l_{bot}}}(\mathsf{pt}),\;
        \texttt{filter\textsubscript{p}}\left(\denote{\mathtt{l_{top}}}(\mathsf{pt})\right)
      \right) \\[2pt]
    \denote{\texttt{Draw(l, s, p, c)}}(\mathsf{pt})
    &= \mathtt{blend_p}\left(\denote{\mathtt{l}(\mathsf{pt})},\;
      \texttt{filter\textsubscript{p}}\left(
       \begin{cases}
         \mathtt{fill_p}(\mathsf{pt}) & \mathsf{pt} \in \mathtt{s} \cap \mathtt{c} \\
         \mathsf{Transparent} & \textsf{otherwise}
       \end{cases}
       \right)\right)\\
  \end{align*}
  \caption{}
  \label{fig:denote}
\end{figure}

Skia has two core operations:
  drawing a shape onto an image,
  and blending two images (representing two layers) into one.
Each operation is parameterized by a \textsf{Paint} object,
  which indicates the current blend mode,
  the fill type, and so on;
  drawing also requires the clip region from the canvas state.
The signatures for each operation are defined
  in \Cref{fig:layer} as constructors of
  a \textsf{Layer} type.
Equivalence of two \textsf{Layer} terms
  is defined by equivalence of their denotations to \textsf{Image}s.

The operations can be denoted to the abstract model,
  as shown in \Cref{fig:denote}.
\textsf{Empty} has a straightforward denotation
  to an all-\textsf{Transparent} image.
\textsf{BlendLayer} is likewise straightforward,
  applying a blend operator, determined by the paint $p$,
  point-wise on the two layers being blended.
\textsf{Draw} is most complex.
Conceptually, it first performs clipping,
  constructing the intersection $s \cap c$
  of the drawn shape and the clip state;
  then it performs filling,
  computing the fill color for each point in the shape;
  and finally it performs blending
  on the original color and computed fill for each point.
The blend is performed
  even for points outside $s \cap c$;
  this is critical for, for example, \textsf{DstIn} blending.
Note that the equalities over denotations are compositional.
That is, if we know that $\denote{l} = \denote{l}$,
  then $\denote{m} = \denote{m[l/l']}$.
The fact that denotations are composable means
  we can use equalities over denotations as rewrites,
  enabling us to actually use our semantics
  to verify optimizations.

\muskia is a simplified version of the Skia API.
A \muskia program consists
  of a sequence of commands
  whose syntax is defined in \Cref{fig:muskia}.
\muskia includes the critical features
  described in \Cref{sec:skia},
  such as the \textsf{Draw} command for drawing,
  the \textsf{Clip} command for manipulating the clip state,
  and the \textsf{Save}, \textsf{SaveLayer}, and \textsf{Restore}
  stack manipulation commands,
\muskia diverges from the full Skia API
  in two main ways.
First, the syntax definition is more regular
  to eliminate unimportant special cases:
  \textsf{Save}, \textsf{SaveLayer}, and \textsf{Restore}
  must be properly bracketed,
  and the \texttt{Draw} and \texttt{Clip} commands
  take arbitrary \textsf{Geometry}s,
Second, only a small fraction of the API is modeled.
Nonetheless,
  extending \muskia to cover more of the API is straightforward,
  and our Lean formalization includes additional features
  such as opacity, styles, and transforms.

\muskia programs manipulate a state $\Sigma$:
\[
\Sigma:\textsf{List[Layer]} \times \textsf{List[Geometry]}
\]
The first list in $\Sigma$ is the stack of layers
  manipulated by \textsf{SaveLayer},
  while the second list is the stack of canvas states
  manipulated by \textsf{Save}.
In this paper, the canvas state is a single \textsf{Geometry}
  because the only canvas operation is \textsf{Clip},
  but in our Lean formalization the canvas state
  includes additional fields.
As is standard, we treat the head of the list
  as the top of the stack.
The initial state is
  $\langle [ \texttt{Empty()} ], [ \mathcal{U} ] \rangle$,
  an empty layer and the full clip state,
  each as single-element stacks.
A \muskia program then performs
  a sequence of steps  $(c, \Sigma) \longmapsto \Sigma'$,
  after which the final state
  consists of a single layer $L$,
  which is the output image,
  and some clip state, which is discarded.
  
We now describe the core steps
  in the operational semantics.
The simplest is the \textsf{Draw} command,
  which modifies the top \textsf{Layer}:
\begin{mathpar}
  \inferrule
  { }
  {
    \langle
    \texttt{Draw(g, p)},
    \langle l :: L, c :: C \rangle
    \rangle
    \;\longmapsto\;
    \langle \texttt{Draw(l, g, p, c)} :: L, c :: C \rangle
  }
\end{mathpar}
\noindent
Note that the \textsf{Draw} operation on the top \textsf{Layer}
  includes both the \textsf{Geometry} and \textsf{Paint}
  from the \textsf{Draw} command
  as well as the current clip from the canvas state:

The \textsf{Clip} command likewise modifies
  the top canvas state, intersecting it
  with the new clip geometry:
\begin{mathpar}
  \inferrule
  { }
  {
    \langle
    \texttt{Clip(c')},
    \langle L, c :: C\rangle
    \rangle
    \;\longmapsto\;
    \langle L, c \cap c' :: C \rangle
  }
\end{mathpar}
\noindent
Note that the full Skia API includes a
  \texttt{SkClipOp} parameter
  that allows instead taking the difference
  between the current and new clip;
  this paper does not show that (straightforward) extension
  but our Lean formalization does include it.

The \textsf{Save} command
  duplicates the top canvas state.
Then, when its matching \textsf{Restore} is reached,
  that top canvas state is discarded:
\begin{mathpar}
  \inferrule
  {
    \langle
    \texttt{cmd},
    \langle L, c :: c :: C \rangle
    \rangle
    \;\longmapsto\;
    \langle L', c' :: c :: C \rangle
  }
  {
    \langle
    \texttt{Save(); cmd; Restore()},
    \langle L, c :: C\rangle
    \rangle
    \;\longmapsto\;
    \langle L', c :: C \rangle
  }
\end{mathpar}
\noindent
Note that it does not make
  any changes to the layer state.

The \textsf{SaveLayer} command, meanwhile,
  allocates a new, empty layer
  for the top of the layer stack and,
  when the \textsf{Restore} command is reached,
  blends that new layer with the one below:
\begin{mathpar}
  \inferrule
  {
    \langle
    \texttt{cmd},
    \langle \texttt{Empty()} :: l :: L, c :: c :: C \rangle \rangle
    \;\longmapsto\;
    \langle l' :: l :: L, c' :: c :: C \rangle
  }
  {
    \langle
    \texttt{SaveLayer(p); cmd; Restore()},
    \langle l :: L, c :: C\rangle
    \rangle
    \;\longmapsto\;
    \langle \texttt{BlendLayer(l, l', p)} :: L, c :: C \rangle
  }
\end{mathpar}
\noindent
The inference rule for sequential composition is straightforward
  and, along with various extensions to \muskia,
  is given in our Lean formalization,
  which we intend to submit as an artifact.

The \muskia semantics is deterministic,
  and programs never get stuck.
Equivalence of \muskia programs,
  which we notate $\eqimg$,
  is defined as equivalence of their final images.
This equivalence relation is \emph{not}
  closed under composition or substitution in general,
  but it is closed under substitution under \textsf{SaveLayer} commands.

\subsection{Rewrites in \muskia}
\label{subsec:rewrites}

This section provides a number of case studies,
  using the \muskia semantics to prove
  equivalences between \muskia programs.
It demonstrates that the \muskia semantics
  are sufficiently powerful to define and prove
  valuable optimizations on real-world Skia programs.
Specifically, we collected the Skia programs
  used by Google Chrome ???\todo{give version number}
  to render the Alexa Top 100 websites
  and examined them to find common, suboptimal patterns.
In general, the suboptimality comes from
  using more \textsf{SaveLayer} commands then necessary,
  and thus both using more GPU memory
  and also performing more blends
  than would otherwise be required.
To demonstrate the flexibility of the \muskia semantics,
  this section shows both general-purpose rewrites
  that apply to a vast range of Skia programs
  as well as more specific rewrites that we expect to apply
  only to Skia programs produced by Google Chrome
  or only to specific web frameworks or even websites.

\subsubsection{SrcOver \textsf{SaveLayer}s}
\label{subsubsec:src-over-layer}

\textsf{SrcOver} is by far the most common blend mode,
  corresponding to the normal intuitive meaning of
  ``drawing over'' some other image,
  and \textsf{SaveLayer}s with \textsf{SrcOver} blend mode
  are often unnecessary,
  suggesting the following idealized equivalence:
\begin{center}
  \small
  \begin{tabular}{T c T}
    \begin{tabular}{@{}l@{}}
      ... // l\textsubscript{1} \\
      SaveLayer(Paint($p$, SrcOver)); \\
      \quad ... // l\textsubscript{2} \\
      Restore()
    \end{tabular}
    & \eqimg &
    \begin{tabular}{@{}l@{}}
      ... // l\textsubscript{1} \\
      Save(); \\
      \quad ... // l\textsubscript{2} \\
      Restore()
    \end{tabular}
  \end{tabular}
\end{center}
\noindent
Specifically, we expect this equivalence to hold
  when the commands labeled $\ell_2$
  all use \textsf{SrcOver} blend mode.
Note that this equivalence replaces
  the \textsf{SaveLayer} command
  by an equivalent \textsf{Save} command
  instead of removing it entirely.
This is necessary to allow
  commands in $\ell_2$ to change the canvas state.
\textsf{Save} is much cheaper to execute than \textsf{SaveLayer},
  since it does not require allocating a new GPU surface,
  so this equivalence still, in practice,
  significantly cuts computation time.

This equivalence is proven by induction
  over commands in $\ell_2$.
It is convenient to assume
  that sequential composition is left-associated
  (we do this in our Lean formalization)\todo{Do we?};
  this means the induction effectively proceeds by
  ``pealing off'' the last drawing command in $\ell_2$.
After expanding out the \muskia semantics,
  the inductive step requires proving
  the following equivalence of \textsf{Layer} terms:
\begin{center}
  \small
  \begin{tabular}{T c T}
    \begin{tabular}{@{}l@{}}
      BlendLayer( \\
      \quad l\textsubscript{1} \\
      \quad Draw(l\textsubscript{2}, g, (SrcOver), c), \\
      \quad (srcover))
    \end{tabular}
    & \eqimg &
    \begin{tabular}{@{}l@{}}
      Draw( \\
      \quad BlendLayer(l\textsubscript{1}, l\textsubscript{2} p), \\
      \quad g, p, c)
    \end{tabular}
  \end{tabular}
\end{center}
Note the \textsf{Draw} command uses a \textsf{SrcOver} blend;
  this is why the commands in $\ell_2$
  must all use \textsf{SrcOver} blends.
Applying this rewrite once ``peals'' a single \textsf{Draw} command
  out of the inner \textsf{SaveLayer}.
Applying it repeatedly results in the original equivalence
  of \muskia programs.

This equivalence is, in turn,
  equivalent to the following equality in our abstract model,
  which asserts that \textsf{SrcOver} blends are associative:
\begin{equation*}
  \srcover(a, \srcover(b, c)) = \srcover(\srcover(a, b), c)
\end{equation*}
In our Lean formalization,
  we provide an instantiation of our abstract model
  using real-valued coordinates and real-valued colors,
  and prove this equivalence
  (including in the case of partial transparency).
There is also a base case to the recursion,
  involving a \textsf{BlendLayer} of an \textsf{Empty} \textsf{Layer}.
One could optionally prove the case
  of a \textsf{BlendLayer} of a \textsf{BlendLayer} \textsf{Layer},
  but we did not see such Skia programs generated by Chrome.

\subsubsection{SrcOver \texttt{saveLayer} redux}
\label{subsubsec:src-over-layer}

A common pattern in Skia programs generated by Chrome
  is grouping a bunch of \texttt{SrcOver} draws
  under a \texttt{SaveLayer} with a \texttt{SrcOver} paint.
Visually,
  this is equivalent to simply performing all draws in the \texttt{SaveLayer}
  instead on the layer below.

\begin{center}
  \small
  \begin{tabular}{T c T}
    \begin{tabular}{@{}l@{}}
      ... // l\textsubscript{1} \\
      SaveLayer(Paint(, SrcOver)); \\
      \quad ... // l\textsubscript{2} \\
      \quad Draw(g, p); \\
      Restore()
    \end{tabular}
    & \eqimg &
    \begin{tabular}{@{}l@{}}
      ... // l\textsubscript{1} \\
      Save(); \\
      \quad ... // l\textsubscript{2} \\
      \quad Draw(g, p); \\
      Restore()
    \end{tabular}
  \end{tabular}
\end{center}

To prove this rewrite, we split it into two separate rewrites over
  \textsf{Layer} terms.
The first rewrite moves the last draw out of \texttt{BlendLayer}.

\begin{center}
  \small
  \begin{tabular}{T c T}
    \begin{tabular}{@{}l@{}}
      BlendLayer( \\
      \quad l\textsubscript{1} \\
      \quad Draw(l\textsubscript{2}, g, p, c), \\
      \quad (srcover))
    \end{tabular}
    & \eqimg &
    \begin{tabular}{@{}l@{}}
      Draw( \\
      \quad BlendLayer(l\textsubscript{1}, l\textsubscript{2}, (srcover)), \\
      \quad g, p, c)
    \end{tabular}
  \end{tabular}
\end{center}

Following denotational semantics of \layer terms,
  the proof of this equality reduces to proving the following equality composition of blend
  modes.

\begin{equation*}
  srcover(\denote{l1}(pt), bm(\denote{l2}(pt), fill(pt))) =
  bm(srcover(\denote{l1}(pt), \denote{l2}(pt)), fill(pt))
\end{equation*}

It turns out that this equality is not true for a general blend mode,
  bm.
But if bm is specfically srcover,
  then this equality is true.
This in turn refines our original statement:

\begin{center}
  \small
  \begin{tabular}{T c T}
    \begin{tabular}{@{}l@{}}
      BlendLayer( \\
      \quad l\textsubscript{1} \\
      \quad Draw(l\textsubscript{2}, g, (srcover), c), \\
      \quad (srcover))
    \end{tabular}
    & \eqimg &
    \begin{tabular}{@{}l@{}}
      Draw( \\
      \quad BlendLayer(l\textsubscript{1}, l\textsubscript{2}, (srcover)), \\
      \quad g, (srcover), c)
    \end{tabular}
  \end{tabular}
\end{center}

This implies we can only peel away the last srcver draw inside a savelayer.
Now if \textit{all} the draws in a savelayer are srcover,
  then we can peel away all of them,
  leaving us with a empty srcover,
  which we can simply remove.


\begin{center}
  \small
  \begin{tabular}{T c T}
    \begin{tabular}{@{}l@{}}
      BlendLayer(l, Empty(), (srcover))
    \end{tabular}
    & \eqimg &
    \begin{tabular}{@{}l@{}}
      l
    \end{tabular}
  \end{tabular}
\end{center}

The proof of this equality follows from the following provable fact about the
  \texttt{srcover} blend mode.

\begin{equation*}
  srcover(\denote{l1}(pt), \textsf{Transparent}) = \denote{l1}(pt)
\end{equation*}

So with the following rewrites,
  we can remove a srcover savelayer so long as
  all the draws inside the savelayer are also srcover.%
\footnote{If we also include opacity, then we must also restrict the savelayer
  to be opaque. We have formalized this restriction in our mechanization.}

\begin{center}
  \begin{tabular}{T c T}
    \multicolumn{3}{c}{\(\forall\,\texttt{cmd}\in\texttt{cmds},\ \texttt{cmd is srcover}\)}\\[0.4em]
    {\small
    \begin{tabular}{@{}l@{}}
      ... // l\textsubscript{1} \\
      SaveLayer(Paint(, SrcOver)); \\
      \quad ...cmds // l\textsubscript{2} \\
      \quad Draw(g, p(SrcOver)); \\
      Restore()
    \end{tabular}}
    & \eqimg
    & {\small
      \begin{tabular}{@{}l@{}}
        ... // l\textsubscript{1} \\
        Save(); \\
        \quad ...cmds // l\textsubscript{2} \\
        \quad Draw(g, p(SrcOver)); \\
        Restore()
      \end{tabular}}
  \end{tabular}
\end{center}

While our refinement is less general than our original rewrite,
  in \Cref{sec:eval} we show that our refinement still shows up
  in a bunch of websites.

One aspect of the original rewrite that is lost in translation to \layer
  terms, is the replacement of \texttt{SaveLayer} with \texttt{Save}.
When we convert terms in \muskia to \layer,
  we make the clip state for a \muskia command explicit in its \layer term.
Which means while we do not need to worry about clips in \layer,
  we cannot be as flippant with them in \muskia.
If we look at the operational semantics of \muskia,
  we can see that while \texttt{SaveLayer} creates a new layer,
  both \texttt{SaveLayer} and \texttt{Save} duplicate the clip state.
Which means as far as clip state goes,
  \texttt{SaveLayer} and \texttt{Save} are equivalent.
So in the \muskia rewrite,
  we replace \texttt{SaveLayer} with \texttt{Save}.
This is a trick we employ in later rewrites too.

\subsubsection{Gradient Masks}
\label{subsubsec:grad-masks}

While the previous rewrite was a common one found across websites,
  the rewrite we are discussing now is specific to the framework
  used by popular Russian websites, \texttt{mail.ru}, \texttt{dzen.ru},
  and \texttt{yandex.ru}.

\begin{center}
  \small
  \begin{tabular}{T c T}
    \begin{tabular}{@{}l@{}}
      Draw(solid fill, srcover);\\
      SaveLayer(DstIn);\\
      \quad Draw(Gradient(opaque));\\
      Restore()
    \end{tabular}
    & \eqimg &
    \begin{tabular}{@{}l@{}}
      Draw(solid fill, srcover);
    \end{tabular}
  \end{tabular}
\end{center}

We saw this pattern used specifically to draw the backdrops of image cards.
The intent seems to be to mask in a very faint gradient
  onto the rectangle backing the image card.
Note that there are no commands before the first Draw.
This is because the entire pattern resides inside a savelayer.
As the type of the savelayer does not matter,
  nor do we change it anyway,
  because of the composibility of rewrites under denotation,
  we elide it from the rule.
This rewrite reduces to proving the following statement:

\begin{equation*}
dstin(srcover(Transparent, fill1(pt)), fill2(pt)) = srcover(Transparent, fill1(pt))
\end{equation*}

If we recall what dstin blending does,
  wed remember that dstin blending an opaque pixel masks in,
  while dstin blending a transparent pixel masks out.
Therefore,
  this statement is only true when fill2 is opaque for all points.
When is a full fully opaque?
This is easy to answer for solid fills,
  we just check the opacity of the single color.
For gradients,
  we instead have to check if every color stop defining the gradient is opaque,
  which is easy to do.%
\footnote{For more complicated fills like images, we could pessimistically assume
  them to not be opaque. Skia could also help in gathering metadata for better
  answers to this question. For example, for the GIF image format, the GCE
  (Graphics Control Extension) block has a \texttt{Transparent Color Index}
  which marks whether transparent pixels are used in the image or not.}
So,
  we can refine our earlier statement to say:

\begin{align*}
  &\forall pt,\, is\_opaque(fill(pt))\\
  &\vdash\\
  &dstin(..., fill(pt)) = fill(pt)
\end{align*}

Which refines our original rewrite to,

\begin{center}
  \small
  \begin{tabular}{T c T}
    \multicolumn{3}{c}{all color stops in gradient are opaque}\\[0.4em]
    \begin{tabular}{@{}l@{}}
      Draw(solid fill, srcover);\\
      SaveLayer(DstIn);\\
      \quad Draw(Gradient(opaque));\\
      Restore()
    \end{tabular}
    & \eqimg &
    \begin{tabular}{@{}l@{}}
      Draw(solid fill, srcover);
    \end{tabular}
  \end{tabular}
\end{center}

  \end{minipage}
  \caption{SVG snippet used in this subsection, shown alongside its rendered result.}
  \label{fig:subsume-svg}
\end{figure}

This SVG program,
  in short,
  fills a rectangle with a complicated gradient.
It then masks in the Canva logo onto the gradient.
This is a pattern we have seen before in \Cref{sec:skia}.
Specifically,
  the mask is implemented using a savelayer with a dstin blend,
  when the svg is lowered to Skia commands.
But,
  the conversion is not that straightforward.
The default masking method for SVG drawings is luminance masking.
That is, white pixels(the brightest color) masks in and black pixels(the darkest
  color) masks out.
If we recall dstin blending, dstin blending is opacity based.
So we need to convert white pixels into opaque pixels,
  and black pixels to transparent pixels.
Skia does this using a luminance filter.

\begin{center}
  \begin{tabular}{T c T}
    {\small
    \begin{tabular}{@{}l@{}}
      ... \\
      draw \\
      savelayer dstin \\
      savelayer lumafilter \\
      draw mask white \\
      restore \\
      restore
    \end{tabular}}
    & \eqimg
    & {\small
      \begin{tabular}{@{}l@{}}
        ... \\
        draw \\
        savelayer dstin \\
        draw mask opaque \\
        restore
      \end{tabular}}
  \end{tabular}
\end{center}

Now if the mask is simple i.e. we only mask one shape and not complex
  intersection of many shapes,
  we should be able to push in filter into the color of the mask.
Which is why our rewrite removes the savelayer filter,
  while also chaing the color of the mask.
We can reduce our \muskia rewrite into a layer rewrite,
  and we have to prove this statement.

\begin{equation*}
srcover(l1, luma(srcover(Transparent, fill))) = srcover(l1, srcover(Transparent,
luma(fill)))
\end{equation*}

We can prove this equality correct,
  because we can prove that srcovering a pixel over the transparent pixel
  is equivalent to just drawing the pixel.
One thing we elide, is the case when we are out of the shape we are trying to
  draw.
Then our equation looks kind of like this

\begin{equation*}
srcover(l1, luma(srcover(Transparent, Transparent))) = srcover(l1, srcover(Transparent,
luma(Transparent)))
\end{equation*}

So it is important to note that we can only move filters which have the
  Transparent pixel as the identity pixel.
This is true for the luminance filter that Skia emits.
