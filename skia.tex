\section{Skia}
\label{sec:skia}

\pavel{make sure we dont reference colors}

Skia is a widely used 2D graphics library.
Skia's basic APIs
  create drawable 2D ``surfaces'' and ``layers'',
  draw shapes to those surfaces and layers,
  blend them together,
  and apply effects.
These
  operations are issued through methods on a \SkCanvas,
  which manages the drawing state.
At execution time, the behavior is backend-dependent:
  CPU backends apply draws
  directly to CPU-visible pixel memory,
  while GPU backends enqueue work that is flushed to backend API objects,
  and then submitted for GPU execution.
But in either case,
  this list of commands issued prior to rendering
  can be stored in an intermeddiate buffer of commands
  to be use for either serialization, replaying, or optimizations,
  which we can take to be a stand-alone programming language.
This section introduces the language's basic operations.

\label{subsec:drawing-painting}

\noindent
Here the layout is meant to evoke
  a Hoare triple:
the left square shows the (empty) state of the canvas
  before the \SkDrawRect command,
  while the right square shows the state of the canvas afterwards.
The \SkDrawRect command needs the bounds of the rectangle
  that needs to be drawn.
\SkDrawRect also takes a \skpaint
  as an argument.
A \SkPaint describes \emph{how} a geometry is drawn,
  for example how to \emph{fill} the geometry.
The default fill for a \SkPaint is the color black,
  but we can also change it to another color.

\noindent
Skia also supports complex fills like images and shaders.
  Formally, filling is a stage of Skia's drawing pipeline
  that assigns a color to every point in the shape.

\subsection{Blending}
\label{subsec:blending}

Things get a little more interesting
  once there is more than one shape being drawn.
Suppose we draw a second, overlapping, blue square:

% paint.setColor(SK_ColorBLUE);
% canvas->drawRect(SkRect::MakeXYWH(120, 120, 136, 136), paint);

In Skia, the process of drawing this second shape
  involves, conceptually, two stages.
First, as before, every pixel in \texttt{Rect2}
  is assigned a fill color, here a solid blue.
Second, this assigned fill color is \emph{blended}
  with the existing color for that pixel.
The default \emph{blend mode}, called \texttt{SrcOver},
  just chooses the new color,%
\footnote{In reality, the blending is more complicated
  and depends on the opacity or \emph{alpha}
  of the new color,
  which can matter for anti-aliasing,
  but in our examples all the colors are opaque
  and we ignore anti-aliasing as a simplification.}
  but a program can select a different blend modes instead.
For example, the \texttt{Multiply} blend mode
  combines both colors being blended:

\begin{figure}[H]
  \centering
  \begin{tabular}{c}
    \frame{\includegraphics[scale=0.26]{drawing2.pdf}}
  \end{tabular}
  \quad
  \begin{tabular}{>{\smaller}T}
    p.setColor(SK\_ColorBLUE);\\
    p.setBlendMode(\\
    \quad SkBlendMode::kMultiply\\
    );\\
    canvas->drawRect(rect2, p);
  \end{tabular}
  \quad
  \begin{tabular}{c}
    \frame{\includegraphics[scale=0.26]{drawing5.pdf}}
  \end{tabular}
\end{figure}

Now, in the intersection of the two rectangles,
  the initial red color is blended with the newly-drawn blue fill,
  which in the \texttt{Multiply} blend mode results in black.
Formally, blending is another stage in the Skia drawing pipeline,
  which comes after filling and combines
  the fill color assigned to each pixel
  with the pre-existing color of that pixel.

\subsection{Clipping}
\label{subsec:clipping}

So far, \texttt{drawRect} has been applying the fill
  to the entirety of the shape being drawn.
But, sometimes,
  we need more granual control over the drawing bounds.
Skia provides a dedicated \texttt{clipRect} command
  to restrict or \emph{clip} shapes to rectangles.%
\footnote{
  Skia allows clipping with arbitrary shapes,
  but the GPU back-end has fast paths for rectangles
  and rounded-rectangles, reducing them to scissor tests}
One uses \texttt{clipRect} like this:

\begin{figure}[H]
  \centering
  \begin{tabular}{c}
    \frame{\includegraphics[scale=0.26]{drawing0.pdf}}
  \end{tabular}
  \quad
  \begin{tabular}{>{\smaller}T}
    canvas->clipRect(c\_rect);\\
    canvas->drawRect(rect1, redPaint);
  \end{tabular}
  \quad
  \begin{tabular}{c}
    \frame{\includegraphics[scale=0.26]{drawing6.pdf}}
  \end{tabular}
\end{figure}

\noindent
Note the unusual order of operations here.
The \texttt{clipRect} command is run first,
  and it does not modify the image at all.
Instead, it modifies the shape drawn
  by \emph{later} draw operations.
Formally, clipping is yet another stage of the Skia drawing pipeline;
  it comes before filling and modifies the shape being drawn.

Semantically, \texttt{clipRect} modifies the \emph{clip state},
  which stored in the canvas object and affects drawing commands.
This means that a single \texttt{clipRect} operation
  can affect multiple \texttt{drawRect} operations:

\begin{figure}[H]
  \centering
  \begin{tabular}{c}
    \frame{\includegraphics[scale=0.26]{drawing0.pdf}}
  \end{tabular}
  \quad
  \begin{tabular}{>{\smaller}T}
    canvas->clipRect(c\_rect);\\
    canvas->drawRect(rect1, redPaint);\\
    canvas->drawRect(rect2, bluePaint);
  \end{tabular}
  \quad
  \begin{tabular}{c}
    \frame{\includegraphics[scale=0.26]{drawing7.pdf}}
  \end{tabular}
\end{figure}

Naturally, one might want to clip
  only a subset of drawing commands.
Luckily, Skia maintains a \emph{stack} of clip states;
  \texttt{clipRect} affects the top of the stack,
  which is used by drawing commands,
  while \texttt{save} and \texttt{restore} commands
  push and pop from the stack.
  \texttt{save} and \texttt{restore} act like brackets,
  restricting the effect of \texttt{clip} to the enclosed commands:

\begin{figure}[H]
  \centering
  \begin{tabular}{c}
    \frame{\includegraphics[scale=0.26]{drawing0.pdf}}
  \end{tabular}
  \quad
  \begin{tabular}{>{\smaller}T}
    canvas->save();\\
    canvas->clipRect(c\_rect);\\
    canvas->drawRect(rect1, redPaint);\\
    canvas->restore();\\
    canvas->drawRect(rect2, bluePaint);
  \end{tabular}
  \quad
  \begin{tabular}{c}
    \frame{\includegraphics[scale=0.26]{drawing8.pdf}}
  \end{tabular}
\end{figure}

Semantically, you can think of \texttt{SaveLayer} commands
  as re-associating the order of blend operations.
In the \texttt{Save} example,
  the order of operations is

\begin{equation*}
  \textsf{blend}(\textsf{blend}(\textsf{empty}, \textsf{red}), \textsf{blue}),
\end{equation*}

While in the \texttt{SaveLayer} example
  the order of operations is

\begin{equation*}
  \textsf{blend}(\textsf{blend}(\textsf{empty}, \textsf{red}), \textsf{blend}(\textsf{empty}, \textsf{blue})).
\end{equation*}

With \texttt{SrcOver} blending, which is associative,
  this order of operations is not important,
  but with other blend modes it becomes significant.
For example,
  we reepat the previous snippet,
  but pass a \texttt{Multiply} blend mode to the \texttt{saveLayer} command.

\subsubsection{Masking}
\label{subsubsec:masking}

To further motivate the need for \texttt{saveLayers},
  consider masking again.
In \Cref{subsec:clipping} we saw how we can use
  \texttt{clipRect} to mask images.
This works when we only need to mask by a rectangle.
But masking with complicated shapes is hard with just clipping.
Instead of trying to clip directly with a complicated shape,
  we can instead draw the clip shape in stages on a seperate layer
  and mask using that shape.

\subsection{Equivalences}
\label{subsec:equivalences}

In \Cref{subsubsec:balh} we saw how complex masks
  can be done with ease using a \texttt{saveLayer}
  with \texttt{DstIn} blending.
But what if just a rectangle mask is needed?
Our \texttt{saveLayer} and \texttt{DstIn} program would still work.
But,
  it is clearly less performant than just doing a clip;
We have to allocate a whole new layer,
  just to do something Skia alreayd has a fast path for!
Here,
  we have two different skia programs that produce the same image,
  but one us clearly a better choice than the other.

\begin{figure}[H]
  \centering
  \begin{tabular}{c}
    \frame{\includegraphics[scale=0.26]{mandrill.pdf}}
  \end{tabular}
  \quad
  \begin{tabular}{c}
    \begin{tabular}{>{\smaller}T}
      restore(); // multiply blending
    \end{tabular}\\[0.8em]
    \begin{tabular}{>{\smaller}T}
      restore(); // second program
    \end{tabular}
  \end{tabular}
  \quad
  \begin{tabular}{c}
    \frame{\includegraphics[scale=0.26]{simple_mandrill.pdf}}
  \end{tabular}
\end{figure}

Therefore it should be possible to replace a skia program
  with a faster one,
  given they have indentical results.
In \Cref{sec:semantics}
  we develop a semantics,
  which allows proving that two Skia programs have identical results,
  including verifying general-purpose rewrite rules.
\Cref{sec:compiler} then uses these rewrites
  to build a general-purpose Skia optimizer
  that rewrites programs to reduce the use
  of multiple layers.
\Cref{sec:eval} then shows that this compiler
  results in dramatically faster rendering
  on a wide range of real-world Skia programs.
