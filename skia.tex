\section{Skia}
\label{sec:skia}

\todo[inline]{make sure we dont reference colors}

Skia's basic APIs
  create drawable 2D ``surfaces'' and ``layers'',
  draw shapes to those surfaces and layers,
  blend surfaces together,
  and apply effects.
These APIs are accessed by calling methods
  on a Skia \texttt{SkCanvas} object;
  however, internally, these \texttt{SkCanvas} operations
  just append commands to a command buffer,%
\footnote{
More specifically, the GPU backend does this;
  there is a CPU backend that does execute commands eagerly.
Since the GPU backend is the fastest and most widely used,
  this paper won't distinguish between Skia and the GPU backend.
}
  which we can take to be a stand-alone program.
The program is actually executed when the \texttt{flush} method is called.
This section introduce the basics of the Skia's drawing API.

\subsection{Drawing and Painting}

The \texttt{drawRect} command is used to draw shapes:%
\footnote{
\texttt{drawRect} and other commands we discuss in this section
  are methods of the \texttt{SkCanvas} object you draw on.
We forgoe the method-call syntax in the examples in this section
  to make them terse.
}

More complex fills like image fills or shaders are also possible.
Formally, filling is one stage of Skia's drawing pipeline,
  which assigns a color to every point in the shape.

In Skia, the process of drawing a second shape
  involves two conceptual stages.
First, as before, every pixel in \texttt{Rect2}
  is assigned a fill color, here a solid blue.
Second, this assigned fill color is \emph{blended}
  with the existing color for that pixel.
The default \emph{blend mode}, \texttt{SrcOver},
  written explicitly in the example above,
  just chooses the new color,%
\footnote{In reality, the blending is more complicated
  and depends on the opacity or \emph{alpha}
  of the new color,
  which can matter for anti-aliasing,
  but in our examples all the colors are opaque
  and we ignore anti-aliasing as a simplification.}
  but other blend modes can be used instead.

For example,
  we could blend the lower rectangle on to the upper rectangle
  with the \fillin{\texttt{Difference}} blend mode instead.
Now instead of the lower rectangle being drawn on top of the upper rectangle,
  the intersection of the rectangles is now
  \fillin{purple}.~\footnote{\fillin{explanation of the blend mode we are epxlaining}}


\subsection{Clipping}

\texttt{drawRect} has no restrictions on where it can draw
  except for the bounds of the canvas.
But, sometimes,
  we need more granual control over the drawing bounds.
Skia provides a dedicated \texttt{clipRect} command
  to restrict or \textit{clip} shapes to rectangles.
Clipping is yet another stage of the Skia drawing pipeline;
  clipping happens before filling
  and modifies the shape being drawn.%
\footnote{
Skia allows clipping with arbitrary shapes,
  but the GPU back-end has fast paths for rectangles
  and rounded-rectangles, reducing them to scissor tests}

One uses \texttt{clipRect} like this:

\begin{center}
\begin{minipage}[c]{0.45\textwidth}
\begin{BVerbatim}
Clip(Rect2, Intersect);
Draw(Rect1,
      Paint(Color(Red), ..., SrcOver))
\end{BVerbatim}
\end{minipage}\hfill
\begin{minipage}[c]{0.45\textwidth}
\centering
\frame{\includegraphics[scale=0.3]{drawing9.pdf}}
\end{minipage}
\end{center}

Note the unusual order of operations here.
The \texttt{clipRect} command is run first;
  it does not modify the image at all,
  but it modifies the \emph{clip state}, stored in the canvas object,
  that affects all later drawing commands.
Here, for example, a single \texttt{Clip} operation
  affects the next two \texttt{Draw} operations.

Naturally, one might want a clip to apply
  to only one command, not all later commands.
Luckily, Skia allows the user to maintain
  a \emph{stack} of clip states;
  \texttt{clipRect} modifies the top of the stack,
  which is used for drawing commands,
  while the \texttt{save} and \texttt{restore} commands
  push and pop from the stack.
This allows the user to restrict the effects of \texttt{clip}
  to a bracketed group of commands.
Here, for example, the clip applies
  to the first rectangle
  but not to the next one:

\begin{center}
\begin{minipage}[c]{0.45\textwidth}
\begin{BVerbatim}
Save();
  Clip(Rect(64, 64, 192, 192), Intersect);
  Draw(Rect(0, 0, 128, 128),
        Paint(Color((1, 1, 0, 0)), ..., SrcOver));
Restore();
Draw(Rect(128, 128, 256, 256),
      Paint(Color((1, 0, 0, 1)), ..., SrcOver))
\end{BVerbatim}
\end{minipage}\hfill
\begin{minipage}[c]{0.45\textwidth}
\centering

Much like \texttt{save} and \texttt{restore} can save clip state,
  there is also a \texttt{saveLayer} and \texttt{restore} command
  that saves and restores the drawing surface itself.
Conceptually, \texttt{saveLayer} allocates
  a new, empty drawing surface,
  and all drawing commands until the corresponding \texttt{restore}
  draw to this new surface.
Then, when the \texttt{restore} command it reached,
  the whole resulting drawing surface is blended back into
  the original drawing surface;
  the blend mode can be passed as an argument to \texttt{savelayer}.
For example, in the following sequence,
  the blue rectangle is first drawn to a blank surface
  and then the result is blended into the surface below.

Semantically, you can think of \texttt{SaveLayer} commands
  as re-associating the order of blend operations.
In the \texttt{Save} example,
  the order of operations is
\[
\textsf{blend}(\textsf{blend}(\textsf{empty}, \textsf{red}), \textsf{blue}),
\]
  while in the \texttt{SaveLayer} example
  the order of operations is
\[
\textsf{blend}(\textsf{blend}(\textsf{empty}, \textsf{red}), \textsf{blend}(\textsf{empty}, \textsf{blue})).
\]
With \texttt{SrcOver} blending, which is associative,
  this order of operations is not important,
  but with other blend modes it becomes significant.

\subsubsection{Masking}

To further motivate the need for \texttt{saveLayers},
  consider masking again.
In \Cref{subsec:blah} we saw how we can use
  \texttt{clipRect} to mask images.
This works when we only need to mask by a rectangle.
But masking with complicated shapes is hard with just clipping.
Instead,
  we can use \texttt{saveLayer}
  along with the \texttt{DstIn} blend mode

\begin{verbatim*}
mandrill example goes here.
\end{verbatim*}

Here we draw the mask shape
  onto the new layer pushed by \texttt{saveLayer}
  and the \texttt{DstIn} blend in that layer onto
  what we want to mask.
\texttt{DstIn} emulates masking through blending;
When we \texttt{DstIn} one pixel over another,
  an opaque top pixel keeps the bottom pixel,
  and a transparent top pixel removes it.

\subsection{Equivalences}

In \Cref{subsubsec:balh} we saw how complex masks
  can be done with ease using a \texttt{saveLayer}
  with \texttt{DstIn} blending.
But what if just a rectangle mask is needed?
Our \texttt{saveLayer} and \texttt{DstIn} program would still work.
But,
  it is clearly less performant than just doing a clip;
We have to allocate a whole new layer,
  just to do something Skia alreayd has a fast path for!
Here,
  we have two different skia programs that produce the same image,
  but one us clearly a better choice than the other.

\begin{verbatim*}
put mandrill rectangle example here
\end{verbatim*}

Therefore it should be possible to replace a skia program
  with a faster one,
  given they have indentical results.
In \Cref{sec:semantics}
  we develop a semantics,
  which allows proving that two Skia programs have identical results,
  including verifying general-purpose rewrite rules.
\Cref{sec:compiler} then uses these rewrites
  to build a general-purpose Skia optimizer
  that rewrites programs to reduce the use
  of multiple layers and of \texttt{DstIn} blending.
\Cref{sec:eval} then shows that this compiler
  results in dramatically faster rendering
  on a wide range of real-world Skia programs.
