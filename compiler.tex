\section{Compiler}
\label{sec:compiler}

In this section we will discuss the implementation of the rewrite rules
  we have proven in the previous section within Skia.
Given that we have shown our rewrites over terms in \muskia,
  we would like to perform these rewrites within Skia on a similiar
  representation of commands.
As we have discussed before in \Cref{sec:skia},
  the method calls of a \texttt{SkCanvas} object
  can be record in an in memory buffer of commands
  called \texttt{SkRecord}.
\texttt{SkRecord} is a dense collection
  of \texttt{SkRecords} objects.%
\footnote{Confusingly, the collection of the many \texttt{SkRecords} object is a
uses the singular word \texttt{SkRecord}.}
A \texttt{SkRecords} object,
  for example \texttt{SkRecords::DrawRect},
  has a tag to distinguish it from other
  \texttt{SkRecords} objects
  and also contains all the information that the specific
  command needs:
To continue our example,
  a \texttt{SkRecords::DrawRect} object
  will contain a reference to a \texttt{SkRect} object
  which define the bounds of the rectangle being drawn
  and a \texttt{SkPaint}.
The buffer managed by \texttt{SkRecord}
  is actually an array of pointers to \texttt{SkRecords} objects.
The allocation of \texttt{SkRecords} object is taken care of by a
  \texttt{SkArenaAlloc} arena allocator.
 \Cref{fig:skrecord-layout} illustrates the memory layout.
As the \texttt{SkRecord} buffer is the most straightforward way to access the
  Skia API commands before any drawing occurs, all of are rewrites mutate this
  buffer.
\texttt{SkRecord} provides two methods to access the underlying
  \texttt{SkRecords} buffer, \texttt{visit} and \texttt{mutate}.
Both methods also need a functor%
\footnote{Functor here refers to a C++ class that has the function call operator
  overloaded, not the typeclass implementing an algebraic structure in niche
  languages like Haskell.
}
Thes ematchign functors allow us to not only match but do other operations using
  the record before returning the reference.
For the purpose of rewrite matching,
  we only use the \texttt{SkRecords::Is<...>} functor.
\texttt{Is} is templated over \texttt{SkRecords} and all it does is if the
  \texttt{SkRecords} that \texttt{Is} is templated over matches the tag of the
  \texttt{SkRecords} at the index we are visiting, we save a reference to the
  object in the functor.
In short, \texttt{Is<A>} lets us know if the \texttt{SkRecords} object at a
  certain index is \texttt{A}.

Skia provides facilities to serialize the \texttt{SkRecord} buffer
  into a binary format called ``Skia Picture'' or \texttt{skp}.
All information in a \texttt{SkRecord} format required for drawing,
  even images drawn,
  are serialized into a \texttt{skp}.%
\footnote{The only exception to what gets serialized seems to be typefaces.}
Given that \texttt{skp}s are an easy way to debug and inspect
  how Chrome generates Skia programs for specific websites,
  Chrome provides a way to dump \texttt{skp}s for websites:
The \texttt{chrome.gpuBenchmarking.printToSkPicture} method
  dumps \texttt{skps}s of a website to disk.
We use this facility to collect benchmarks for our evaluation
  discussed in more detail in \Cref{sec:eval}
It is important to note here that Chrome can dump multiple \texttt{skp}s for one
  website.
Chrome has a compositing step prior to rendering with Skia,
  wherein it groups different visuals elements of a website
  into a layers.
This is done to reduce the amount of time spent re-rendering
  when something changes on the website;
visual elements that are likely to change together
  are grouped into the same layer.
It is this layer which is converted into a Skia program
  which the browser finally renders onto the screen.
Our optimizer currently only optimizes single layers,
  and does not perform any cross-layer optimizations.
As \texttt{skp}s can be easily read into and from a \texttt{SkRecord} buffer,
  our optimizer takes as input the \texttt{skp} to be optimized,
  and returns an optimized one.

\subsubsection{Mutating \texttt{SkRecord}}

To perform rewrites over a \texttt{SkRecord} buffer,
  we need to be able to change, remove, and add commands
  into the buffer.
Changing commands is easy.
We only need to allocate a new \texttt{SkRecords} object
  in the arena allocator,
  and change the pointer to point to this new object.
Removal is just like changing commands,
  because we just change the command we want to remove
  into a special \texttt{SkRecords::NoOp} object.
Insertion is tricky into a dense array.
Compiler IRs usually are represented as doubly linked lists
  to allow easy constant-time insertion given a location.
As \texttt{SkRecord} is a dense array,
  insertion instead takes linear time,
  because we have to first grow the array to accomadate the new element
  and then shift all elements after the insertion location
  to make space for the new element.
We can do better by amortizing the cost of many insertions.
We do this by storing all the insertions that are to be done.
Then when we have determined all the insertions to be done,
  we allocate space needed for all insertions,
  and in one linear scan shift all the ncessary elements
  and perform all insertions.
This technique has been given the name ``InsertionSet''
  and is employed in the B3 JIT -- which also uses a dense array as its IR
  memory representation -- powering the WebKit browser engine.
We have implemented an InsertionSet in \texttt{SkRecord}
  to facilitate easy insertion of \texttt{SkRecords} objects.

\subsection{Rewrite Matching}

The rewrite we have discussed before in \foo are implemented as
  single-pass matchers over the \texttt{SkRecord} command buffer.
Each matcher iterates through the command buffer,
  maintaining the current state of the matcher on a stack.
  In \foo we show the interface of one of the rewrite matchers we use.

The core of the matching logic is int he \texttt{transform} function that
  mutates a \texttt{SkRecord} buffer.
The structure of the transform --
  an example transform function is listed in \foo{} --
  is quite simple.
It loops through each element of \texttt{SkRecord} in sucession
  and matches on what it is using the \texttt{Is<...>} functor.
At each case,
  what the matcher does depends on the rewrite rule being implemented.
For example,
  in the transform function for the opaque save layer rewrite discussed in \foo,
  its \texttt{Is<SkRecords::SaveLayer>} case would push a \texttt{Matching}
  state onto the stack if the paint of the current savelayer is ever opaque
  srcover else it pushes an \texttt{Ignore}.
The current state of the matcher is maintained by \texttt{state\_stack}.
\texttt{state\_stack} mirrors the layer stack seen in the operational semantics
  in \foo;
\texttt{SaveLayer}s will push matching states onto it, and \texttt{Restore}s
  will pop of it.
As all of our rewrites remove savelayers,
  the actual rewriting occurs when a \texttt{Restore} is seen.
As we only ever do a linear scan of the \texttt{SkRecord} buffer and operations
  to modify the buffer also only ever take linear time, all our transform
  functions run in linear time.
Space-wise one would think the matchers would be linear
  but we have optimized space usage by exploting some quirks in the code
  generated by Chrome.
While Chrome is liberal with its use of \texttt{Save},
  it does try ot ensure it does not nest too many \texttt{SaveLayer}s.
Emprically, we've never seen Chrome nest more than 4 \texttt{SaveLayer}s.
Which means, if we only track the state of \texttt{SaveLayer}s in the
  \texttt{state\_stack}, we should be able to keep all the state information on the stack
  instead of the heap.
Which is why we use Skia's \texttt{STArray<i, T>} vector type,
  which keeps the first \texttt{i} elements of the array on the stack instead
  adn the rest on the heap (ideally we never have to allocate stack states on
  the heap).
We deal with \texttt{save} by just maintaining a count of the number of
  \texttt{save}s seen till now,
  which we also save in the \texttt{state\_stack}.
Then depending the current save count,
  and the save count on the stack,
  we'd know if the \texttt{restore} matches a \texttt{save} or a
  \texttt{savelayer}.
Which means out matcher also does not grow much in space.
The exct stacks, the behaviour of the transform function, and the metadata saved
  in the \texttt{state\_stack} depends on rewrite we are matching.
Beyond these optimizations, we noticed that it was enough just compiling the
  state machine using \texttt{clang} optimization level 3.
We discuss the speed of the optimizer in more detail in \foo.
