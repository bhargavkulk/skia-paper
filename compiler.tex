\section{Compiler}
\label{sec:compiler}

To show that the \muskia semantics
  are useful for developing impactful Skia tooling,
  this section discusses the implementation
  of a Skia optimizer using the rewrite rules
  discussed in \Cref{sec:rewrites}.
Besides correctly implementing the relevant rules,
  the optimizer must also be highly-efficient
  because Skia rasterization must meet a refresh rate target
  and thus has a budget of hundreds to thousands of microseconds,
  of which the optimizer must be a smaller share.
For this reason, the optimizer sometimes implements
  a somewhat-restricted version of the rewrites
  to ensure that it runs a single pass over the Skia command buffer.

\subsection{Memory Management}

When a Skia client calls a methods on the \texttt{SkCanvas} object,
  Skia records this command in an in-memory buffer
  called an \texttt{SkRecord}.
\texttt{SkRecord} is a dense collection
  of \texttt{SkRecords} objects.%
\footnote{
Confusingly,
  the collection of the many \texttt{SkRecords} objects
  uses the singular word \texttt{SkRecord}.
}
Each \texttt{SkRecords} object,
  for example \texttt{SkRecords::DrawRect},
  is distinguished by a tag
  and then has additional fields for
  all the arguments to that specific command.
\texttt{SkRecords::DrawRect}, for example,
  will contain a reference to a \texttt{SkRect} object
  which defines the bounds of the rectangle being drawn
  and an \texttt{SkPaint}.
The \texttt{SkRecord} manages a buffer, which is
  an array of pointers to \texttt{SkRecords} objects,
  each of which is allocated in an
  \texttt{SkArenaAlloc} arena allocator.
 \Cref{fig:skrecord-layout} illustrates the memory layout.
Importantly, this design means that
  the compiler can mutate the \texttt{SkRecord} buffer
  without moving the actual \texttt{SkRecords} objects.

\texttt{SkRecord} provides two methods to access the underlying
  \texttt{SkRecords} buffer, \texttt{visit} and \texttt{mutate}.
Both methods also need a functor.%
\footnote{
Functor here refers to a C++ concept---%
  a class that has the function call operator overloaded---%
  not the unrelated concept in category theory.
}
In general, these functors allow matching and also mutation,
  but we only use the \texttt{SkRecords::Is<...>} functor,
  which performs tag-checking and compiles to an efficient comparison
  while staying type-safe.

Skia can serialize \texttt{SkRecord} objects
  to and from a binary format called a ``Skia Picture'' or \texttt{skp}.
All information in a \texttt{SkRecord} format required for drawing,
  including images, are serialized into a \texttt{skp}.%
\footnote{
An exception seems to be that typefaces do not gets serialized.
}
This allows us to evaluate our optimizer
  without interference from the complex Google Chrome runtime;
  specifically, our evaluation
  reads an \texttt{skp} from disk, optimizes it,
  and writes the optimized \texttt{skp} to a new file.
Note that though the input and optimized output are stored in different files,
  during optimization the optimizer mutates a single \texttt{SkRecord}
  without making any copies.

Importantly, Google Chrome can
  dump its generated Skia programs to disk as \texttt{skp}s
  with the \texttt{chrome.gpuBenchmarking.printToSkPicture} debug method,
  available when Chrome is run with \texttt{--no-sandbox} and
  \texttt{--enable-gpu-benchmarking} flags.
We use this facility to collect benchmarks for our evaluation,
  as discussed in more detail in \Cref{sec:eval}.
It is important to note here that Chrome generates
  multiple Skia programs, meaning multiple \texttt{skp}s,
  for a single website.
These multiple programs represent different ``layers'' of the page,
  which are then composited in a later step;
  this split into layers is important for efficient animations~\cite{wbe}.
The optimizer operates on layers individually,
  and neither performs cross-layer optimizations
  nor influences how Chrome splits a page into layers.

\subsection{Rewriting}

Applying the rewrite rules in \Cref{sec:rewrites}
  requires changeing, removeing, or adding commands in the command buffer.
Changing commands is easy:
  the optimizer allocates a new \texttt{SkRecords} object in the arena
  and changes the buffer to point to this new object.
Removal likewise changes the command to remove
  into a special \texttt{SkRecords::NoOp} command.
Insertion, however, is tricky, because the input command buffer is dense.
Inserted commands are allocated into the arena as normal.
However, to minimize run time,
  the actual insertion into the buffer is delayed.
Instead, all insertions are first made into a separate insertion buffer.
Then, after the compilation pass is complete,
  a new buffer of the right size is allocated
  and a single linear scan is performed
  to merge the original buffer and the insertion buffer.
We learned of this technique from the WebKit browser engine's B3 JIT,
  where it is called an ``InsertionSet''~\cite{insertionset},
  though we believe this technique is well-known.

The remaining complexity of the optimizer consists of
  efficiently finding the relevant patterns in the command buffer.
To maximize performance, it is important that each compilation pass
  performs a single pass over the command buffer.
We implement this single-pass matcher with the $\SkOptPass$ interface we show in
  \Cref{fig:statemachine}.
The main matching logic is handled by the \texttt{transform} method.
The \texttt{transform} method takes as argument a \texttt{SkRecord} buffer,
  does a linear-pass over all \texttt{SkRecords} objects in the buffer.
For every object, it calls the corresponding \texttt{on*} callback method
  (\emph{e.g.} \texttt{transform} will call \texttt{onSaveLayer} on seeing
  a \SaveLayer).
For some special \texttt{SkRecords} objects,
  \texttt{transform} also does a bit beyond just dispatching callback methods.
For \Save,
  \texttt{transform} increments a \texttt{save_count}.
For \SaveLayer,
  \texttt{transform} initializes and pushes a new \texttt{Frame} on a stack.
Before pushing,
  it also saves the current \texttt{save_count} onto the \texttt{Frame}.
And finally,
  for \Restore,
  it pops a \texttt{Frame} depending on the current \texttt{save_count}.
If the current \texttt{save_count} is greater than that of the \texttt{Frame}
  that is on top of the stack, it does not pop of the stack.
This is because, there have been some intermeddiate \Save{}s before the current
  top-of-stack \SaveLayer, and \texttt{transform} should decrement the
  \texttt{save_count} instead of popping from the stack.
This scheme helps us in two ways.
Firstly, this allows us to distinguish between a \Restore of a \Save and a \Restore
  of a \SaveLayer.
Secondly, we only ever push \SaveLayer information onto the stack.
Moreover, as we have not seen deep nesting of \SaveLayer in \texttt{skp}s
  generated by Chrome, we could keep the entire \texttt{Frame} stack on the
  stack instead of the heap.
Which is why we use Skia's \texttt{STArray}, which keeps the first 8 elements on
  the stack.
We further discuss the speed of the optimizer in \Cref{subsec:rq2}.

Now, when \texttt{transform} pushes a \texttt{Frame} onto the stack,
  it also puts a \texttt{MatchState} in the \texttt{Frame}.

A \texttt{MatchState} is state fo the current matcher,
  which needs to be defined by the specfic rewrite matcher.
For example, for the \SrcOver-\SaveLayer rewrite,
  we use two states, \texttt{Matching} and \texttt{Ignore}.
This is basically a small state machine.
\Cref{fig:statemachine} shows the state machine
  for the \srcover \SaveLayer rewrite in \Cref{sec:rewrites}.
For this rewrite, the state machine starts in a matching state
  if the \SaveLayer has a \srcover blend mode
  (and is opaque; our Lean formalization includes opacity)
  and transitions to a non-matching state if any
  non-\SrcOver \Draw commands are observed.
\SaveLayer commands could also
  transition the parent layer to a non-matching state;
  in theory this could be supported but we didn't see this pattern
  in any of our evaluation programs.
Once a \Restore matching a \SaveLayer is seen,
  if the current state is matching,
  the actual rewriting is performed
  by changing the \SaveLayer command
  into a \Save command.
While we only show the state machine for the \SrcOver \SaveLayer rewrite,
  we can and have derived state machines in a straightforward way to implement
  the other rewrites described in \Cref{sec:rewrites}.
