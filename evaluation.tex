We evaluate the \muskia semantics, and the optimizer based on them,
  on a collection of real-world Skia programs
  generated by Google Chrome on the Top 100 websites,
  focusing on four research questions:

\begin{enumerate}
\item[RQ1] Is the optimizer correct? % TV, and pixel diffs (antialisaing)
\item[RQ2] Does the optimizer improve the rasterization time? % render time CDF Metal
\item[RQ3] Is the optimizer fast enough? % time taken to optimize
\item[RQ4] Are the optimizations generic across Skia backends, hardware, and websites? % more CDF
\end{enumerate}

\subsection{Methodology}

We evaluate our optimizer on Skia programs
  generated by Google Chrome on the
  top 100 most-visited websites in the world,%
\footnote{Excluding a few pornographic websites.}
  using the list on Wikipedia~\cite{wiki-top100},
  which in turn is based on data from Similarweb and Semrush.%
\footnote{The famous ``Alexa Top 100'' is no longer produced.}
Google Chrome, via the Playwright, is used to visit
  the main page of each websites,
  and \texttt{skp} files are dumped as described in \Cref{sec:compiler}.
Each website produces one \emph{or more} \texttt{skp} files.
Since our optimizer focuses on reducing
  the number of \texttt{SaveLayer} commands,
  we focus on \texttt{skp} files that have \texttt{SaveLayer} commands.
For our primary evaluation in RQs 1--3,
  this leaves \grmetalnumbench benchmarks across \N websites.

The optimizer itself is based off of Skia commit \texttt{f931a2e},
  on the \texttt{main} branch between milestones 143 and 144~\cite{skia-releases}.
For our primary evaluation in RQs 1--3,
  we build Skia with Clang version 17.0.0 with \texttt{-O3} and \texttt{-flto=thin}
  and run it on an 8-core Apple M2 unified CPU/GPU with 16GB RAM
  and the Metal graphics backend.

\subsection{RQ1: Are the optimizations correct?}

This section aims to answer RQ1 by showing
  that the optimizer is correct,
  in two senses: that it conforms with the \muskia semantics
  and that it also does not introduce visible distortions
  on the evaluation websites.

\subsubsection{Conformance with \muskia Semantics}

To test whether the optimizer conforms with the \muskia semantics,
  we extended it with a mode that outputs an \texttt{skp}
  after each individual rewrite pass,
  forming an ``optimization trace''.
Each of these \texttt{skp} files is then converted
  into a readable JSON format using \texttt{skp\_parser},
  a tool distributed with Skia,
  and then read and converted to \muskia Lean terms
  using a short Python program.
Not every \texttt{skp} can be converted,
  since \muskia does not formalize some advanced Skia features
  like mask and image filters,
  but for \N benchmarks
  all steps in the optimization trace convert cleanly.
The conversion program also performs some minor simplifications,
  such as down-casing \texttt{SkPath} shapes
  to simpler shapes like \texttt{SkRect} when possible,
  to invert a transformation done by Skia.
If all \texttt{skp} file in the optimization trace
  can be converted to a \muskia Lean term,
  a sequence of lemmas is asserted in Lean,
  claiming that each step in the trace
  is equivalent, as a \muskia program, to the previous step.

\begin{figure}
\begin{BVerbatim}
theorem src_eq_opt1 : denote src = denote opt1 := by
  unfold src
  unfold opt1
  grind (gen := 80) [GradientMask]
\end{BVerbatim}
  \caption{
  Example of a translation validation lemma.
    \texttt{src} is the source \muskia term,
    and \texttt{opt1} is the term after one optimization pass.
  The relevant rewrite theorem, \texttt{GradientMask},
    is passed to \texttt{grind} to search for a proof;
    a number of general-purpose \muskia theorems
    are also included by \texttt{@[grind]} annotations.
  The \texttt{gen} argument to \texttt{grind}
    increases its search fuel
    to enable proofs for larger \muskia terms.}
\label{fig:layerTV}
\end{figure}

To prove this theorem, we rely on Lean's \texttt{grind} tactic.
The \texttt{grind} database is loaded with
  theorems for the rewrite rules applied by the optimizer in this step
  as well as general theorems about \muskia equivalence.
\Cref{fig:layerTV} shows an example proof.
Translation validation succeeds for \tvpass benchmarks
  of \grmetalnumbench benchmarks,
  demonstrating that our optimizer conforms with the \muskia semantics
  and providing a ``foundational'' certification of its correctness
  on these benchmarks.
Some of the successful translation validations are quite complex;
  for example, the main \texttt{skp} from Pinterest contains
  a luminance filter nested in a \DstIn mask nested in an opaque \SaveLayer.
Three separate optimization passes fire on this benchmark,
  with each one exposing the next rewrite opportunity;
  all three translation validate.
The remaining \tvgrindtimeout benchmarks
  do not translation validate due to \texttt{grind} timeouts;
  as a general-purpose proof search engine,
  \texttt{grind} is slower than our optimizer
  and times out on complex \muskia terms.


\subsubsection{Optimizations yeield the same images}

Conformance with the \muskia semantics, however,
  is only as good as the quality of the \muskia semantics themselves.
We therefore compare the baseline and optimized \texttt{skp}
  by rendering both \texttt{skp} to PNG images
  and performing a pixel diff using ImageMagick \texttt{compare}.
The \muskia rewrites of \Cref{sec:rewrites}
  are proven in a real-valued abstract model,
  so ignore effects from discretization and anti-aliasing,
  which are caused by the discrete pixel grid and finite color depth,
  so some differing pixels are expected;
  we therefore pass \texttt{-metric AE} and \texttt{-fuzz 1\%}
  to \texttt{compare},
  asking it to report the number of pixels
  that differ by more than \texttt{1\%} in a color channel.
Across the \grmetalnumbench benchmarks,
  only \grmetalpixdif report significant pixel differences,
  and examine all such instances manually;
  \Cref{fig:diff} shows one example, from TikTok.
In all such instances, the differing pixels
  are clearly caused by anti-aliasing,
  as evident by the ``spotted'' nature of differences
  and their location along curved shape edges.
The authors could not tell
  the baseline and optimized rasterizations apart by sight.
Skia does not guarantee its anti-aliasing behavior,
  which can further differ by monitor type or operating system,
  and we confirmed with a member of the Skia team
  that anti-aliasing changes are acceptable.

\subsection{RQ2 Does the otpimnizer improve the render time of real world Skia
  programs?}

To answer this research question,
  we benchmark the rendering time of both the unoptimized and optimized
  \texttt{skp}s of the websites we discussed before.
To measure render time,
  we use \texttt{nanobench}, a benchmarking tool internal to Skia.
\texttt{nanobench} actually has many different benchmarking options,
  the \texttt{skp} \texttt{playback} options are what we use
  to measure render time.
As rendering time is not many magnitudes greater than the timer overhead%
\footnote{\texttt{nanobench} uses \texttt{std::chrono::steady\_clock} as its
  timer.}
  we need to choose a careful ebcnhmarking scheme that is able to factor out
  timer overhead.
We now describe how \texttt{nanobench} avoids that, by talking about the
  measurement scheme.
Before actually measuring the time taken to render for a specific \texttt{skp}
  file, \texttt{nanobench} first measures the number of loops of rendering
  needed to make the timing overhead negligible.
In \texttt{nanobench}, each reported sample is computed as:
  total elapsed time for a run, divided by the number of playback loops in that
  run.
So the key to making the timer overhead neglibible is to choose a good loop
  count.
For GPU playback, \texttt{nanobench}
  calculates the number of loops needed so each sample lasts about a target
  duration (default \texttt{--gpuMs=5} ms):
it doubles loops until the sample exceeds the target, then rescales loops to
  land near that target.
This makes each sample long enough that timer-call overhead is negligible.
Using this scheme, we measure 100 samples for each benchmark, both the optimized
  and unoptimized \texttt{skp}.
We summarize the rendering speedup across 100 samples using their geometric
  mean.
For this research question we only measure rendering time of all benchmarks
  on Machine \#1 running Skia's Graphite/Metal GPU backend.
Graphite is Skia’s new GPU rasterization backend, rebuilt for modern
  graphics APIs (like Metal, Vulkan, and D3D12) with a cleaner architecture and
  multithreaded rendering workflow.
Skia's older GPU backend, Ganesh, targeted GPU's through GL.
% https://blog.chromium.org/2025/07/introducing-skia-graphite-chromes.html
While this section only discusses performance on Graphite,
  in \foo we also show our optimizer's performance on Ganesh as well as other
  hardware platforms in \foo.

The CDF chart in \Cref{grmetal-cdf} plots the optimizer's results.
The X axis of the plot is the speedup --baseline render time / optimized render
  time-- while the Y axis is the percentage of benchmarks that have
  speedup less than or equal to a certain speedup.
On this specific machine-backend combination,
  we see a maximum speedup of \grmetalmaxspeed.
Moreover
Looking at the plot,
  note that most of the CDF line is over the 1$\times$ speedup line.
This means a majority -- here \grmetalpctspeed -- of the benchmarks render faster after being
  optimized.

The long right tail of the CDF plot is due the optimizer significantly improving
  the rendering time of group of russian websites we listed in \foo.
Recall,
  that these russian websites seem to share the web framework,
  and as a result we are able to remove the redundant gradient mask layers
  described in \foo.
Moreover,
  these gradiant mask layers are always inside an opaque save layer,
  which means that the gradient mask layer encovers a new rewrite oppurtunity.

Slowdowns are \grmetalpctslow of the benchmarks.
All of the slowdowns are seen on website with \emph{no matches},
  suggesting all of the slowdowns seen in the left-tail of the CDF
  are all measurement/runtime noise and not caused by our optimizer.

Furthermore,
  all of the significant speedups we see in the CDF plot are due to the
  optimizer, and not measurement/runtime noise.
Specifically,
  out of the \grmetalnumbench benchmarks, \grmetalnumspeed are speedups.
Within these speedups,
  \grmetalnumspmatch are actually optimized by the optimizer.
The range of the speedups of the optimized benchmarks -- \grmetalspmatchmin to \grmetalspmatchmax -- are
  larger than the range of the speeudps of the unoptimized benchmarks --
  \grmetalspnomatchmin to \grmetalspnomatchmax.

In summary,
  our optimizer, which implements the rewrites described \foo,
  improves the rendering time significanlty for real-workd websites.

\subsection{RQ2 Does the optimizer pay for itself}

While our optimizer does speed-up the rendering time large, high traffic
  websites, this rendering time is meaningless if the time taken to optimize
  is slow.
In this section we aim to show that our optimizer pays for itself i.e. the time
  to optimize a \texttt{skp} is always far smaller than the time taken to render
  the optimized \texttt{skp}.
To measure optimziation time, we replicated \texttt{nanobench}'s benchmarking
  scheme we described in \foo.

\subsection{RQ4 Are the optimizations generic across Skia backends, hardware, and
  websites?}

In this section, we want to ask if the optimzer's results are
  generalizable.
We evaluate this along two orthogonal axes of generalizability.
First, \emph{platform generalizability}: do the rewrites help across different
  hardware, GPU APIs, and Skia backends
Second, \emph{workload generazaibility}: do the rewrites help on websites beyond
  thos used to develop the rewrites used in the optimizer

\subsubsection{Platform generalizability}

Here we ask whether our rewrites are specific to one platform,
 or whether they transfer across different hardware and rendering backends.
To test this, we evaluate the optimizer in a 2$\times$2 setting:
   two machines (Machine \#1 (Apple) and Machine \#2 (Intel)) crossed with Skia’s two GPU backends
   (Graphite and Ganesh).
Concretely, we run:

\begin{enumerate}
\item Graphite/Metal and Ganesh/OpenGL on machine \#1
\item Graphite/Vulkan and Ganesh/OpenGL on machine \#2
\end{enumerate}

This experiment reuses the same website-derived benchmark collection process as
  in \Cref{sec:eval-rq2}
  (with per-machine benchmarks determined by Chrome’s platform-dependent compositing behavior).
\Cref{fig:cdfmatrix} shows one CDF per machine/backend pair.
If the optimizer’s gains were backend- or hardware-specific,
  we would expect improvements to disappear in some quadrants.
Instead, we observe improvements across all four settings,
  indicating that the rewrites are not tied to a single GPU API,
  backend implementation, or machine.

In all cases, we notice the same behaviour as in \Cref{sec:eval-rq2}.
The long right-tail is due to the optimizer significantly improving the set of
  russian websites (we see rendering time speedups of up to \grmetalmaxspeed in
  Graphite/Metal, \gaglapmaxspeed in Ganesh/OpenGL-Apple,
  \grvkmaxspeed in Graphite/Vulkan, and \gagleintmaxspeed in
  Ganesh/OpenGL-Intel)
Just like we saw in \foo,
  some benchmarks that show speedups are rewritte by the optimizer,
  but some are not.
The benchmarks that were rewritten show more significant speedups
  than the ones that were not across all hardware/backend pairs.
This means that the rewrites contribute to speedups the most,
  and their speedups are not measurement noise.
Furthermore,
  across all hardware/backend pairs,
  almost all the slowdowns are \emph{not rewritten} by the optimizer i.e.
  the baseline and optimized Skia programs are identitical.
Which means across all hardware/backend pairs,
  our optimizer never incurs slowdowns,
  with the exception of a layer of the website Canva on Ganesh/OpenGL,
  which has a persistent slowdown of \gaglcanvaslowdown.
We have already seen this website before in \foo.
To summarize, this website sees 3 rewrites, each of which enables the next.
First, can remove the luminance filter \SaveLayer which just has a single mask.
Fater performing this rewrite, we now exposes a \DstIn mask.
After performing the \DstIn mask, which moves the mask of the image (here the
  complicated logo of Canva), to a \texttt{clipPath} command, clipping the gradient draws that
  make up the backdrop.
Finally after getting rid of the \DstIn \SaveLayer,
  we now find a opaque SrcOver \SaveLayer, which we also remove.
It turns out,
  that for Ganesh/OpenGl-Intel,
  performing a complicated \texttt{clipPath} is rather expensive and msut be
  avoided.
Our optimizer can just not perform the DstIn mask rewrite for complicated path,
  and only do so for simple geometries like rectangles and rounded-rectangles.
Such a slowdown is understandable, because the specific quirks of
  hardware/backend pairs are out-of-model for our semantics.
Nevertheless,
  the \DstIn mask for Canva is the \emph{only} regression we see across all
  benchmarks.%
\footnote{While machine \#1 and \#2, have slightly different benchmark sets,
  the Canva layer is in both.}
 This means we can confidently claim that our optimizer generalizes over platforms.

\subsubsection{Workload generalizability}

We next ask whether the optimizer generalizes across \emph{workloads},
  not just across platforms.
Here,
  workload means the distribution of website-derived Skia programs.
To test this,
  we keep the optimizer and rewrite order fixed, and evaluate it on
  an out-of-sample website corpus that was not used while developing the
  rewrites.
We chose the next 100 most visited websites in the world (like before, collated
  from web traffic rankings from Semrush and Similarweb).
As we did for the original benchmark set,
  we dumped their \skps from Chrome as described in \foo (This yielded \grmetalnewnumbench benchmarks).
And we ran them in the exact same way as we did the benchmarks in \foo.
Crucially, we do not add any new rewrites rules,
  as we are trying to evaluate the generalizability of the existing rewrite ruleset.
If the optimizer were overfit to the original benchmark set,
  we would expect its gains to disappear or become inconsistent on these new benchmarks.
Hence, we evaluate the same metrics as before (render-time speedup CDF,
  rewritten/non-rewritten breakdown, and regressions) to check whether the same
  performance pattern persists.

Certainly,
  with new benchmarks come new patterns to optimize.
If one would like to come up with new rewrites,
  then one should follow the same process we did.
Which is,
  inspecting the resulting \skps from the websites,
  identifying common patterns amongst them,
  proving an indentified pattern against our the mechanized semantics in Lean,
  and finally implementing it as a rewriter in Skia.
