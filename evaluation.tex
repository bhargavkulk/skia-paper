\subsection{RQ1 Are the optimizations correct?}

In this section we aim to ask, wether the optimizer is \emph{correct}.
This qeustion can be answered in two aces.
Firstly, wether the optimzier
  conforms to the semantics laid out in \Cref{sec:semantics}.
Secondly,
  wether the images rendered by the optimized Skia programs are identical to the
  images rendered unoptimized.
We aim to answer both questions in this section.

\subsubsection{Conforming with semantics}

TO show that our optimizer implemented withing Skis conforms to the semantics,
  we build a translation validator for the optimizer.
The translation validator is built on top of the semantics mechanized in Lean.
As the optimizer applies each rewrite seperaetly and in a specific order,
  our translation validator validate each seperate rewrite pass.
We do this by first dumping the intermeddiate \texttt{skp}s after each rewrite.
We then seralize each of these intermeddiate \texttt{skps}s into a readable JSON
  format using the a tool provided by Skia called \texttt{skp\_parser}.
We then convert these JSON Skia programs into Lean terms with a compiler.
This compiler implements the operational semantics of \muskia as described in
  \foo along with a few clip geometry simplificiations.
The compiler mainly tries to simplify clips, for example simplifying the
  intersection of equal clips.
The compiler also tries to convert Path geoemetries into simpler shape as an
  when possible (Skia does this under the hood).
In the translation validator in Skia,
  we aim to prove each intermeddiate rewrite with a theorem.
For example,
  the first rewrite is the gradient mask rewrite.
So, in Lean,
  we would prove equality of the source Skia program and the intermeddiate Skia
  program generated after performing the gradient mask rewrite.
This is then done sequentially for all the other rewrite passes too.
We prove the theorem only using the already proven rewrite in Lean.
This is fasciliated by the powerful \texttt{grind} tactic in Lean.
\texttt{grind} uses techniques inspired from modenr SMT solvers to automatically
  prove theorems in Lean.
Ir is able to prove facts by trying to apply older facts from a specified
  database of facts.
We restrict the database of facts that \texttt{grind} has access to in order
  reign in the search space.
For example,
  the \texttt{grind} invocation for the proof of the gradient mask rewrite only has the
  gradient mask theorem in its database, similiarly for the other rewrite
  passes.

\begin{figure}
\begin{BVerbatim}
theorem src_eq_opt1 : denote src = denote opt1 := by
  unfold src
  unfold opt1
  grind (gen := 80) [GradientMask]
\end{BVerbatim}

\label{fig:layerTV}

It is important to note that the compiler, and by extension the translation
  validator only supports the fragment of Skia we formalize in \muskia.
That means Skia programs with image filters, blurs, color filters other than
  luminance and so on, will be rejected by the translation validator.
This does not mean that the the programs are unequal, in fact later on in this
  section we show that even programs that are not represented by \muskia
  are not only optimized but also yield the same image.

Across the \macbenchnum benchmarks on machine \#1,
  we sucessfully translation validate \fillin{34} pass translation validation.
In fact, out of the \fillin{42} programs that do pass trasnlation validation,
  all but \fillin{9} programs fail due to \texttt{grind} timeouts.
Our translation validation scheme, proves correct not only simpl programs with
  one type of rewrite, but also programs that have many nested rewrites.
For example,
  the lone layer of Pinterest that has a \texttt{SaveLayer} has three nested
  rewrites:
  a lumninance filter save layer, nested in a \texttt{DstIn} mask, nested in a
  opaque \texttt{SaveLayer}.
Only by sucessfully performing the inner rewrite can you expose a rewrite
  oppurtunity for the next rewrite, and all three nested rewrites are proven
  correct by the translation validator.


\subsubsection{Optimizations yeield the same images}

Beyond just smenatic correctnes, we also show that both baseline and optimized
  Skia programs render to the same PNG image.
We do this by, first rendering Skia programs (both baseline and optimized) into
  PNG files through Skia, and then using ImageMagick's \texttt{compare} tool to
  compare both of them.
We use the options \texttt{-metric AE}, which tells
  \texttt{compare} to compare each pixel and report the number of differring
  pixels, and \texttt{-fuzz 1\%}, which asks for a 1\% tolerance from
  \texttt{compare}.
Across \macbenchnum benchmarks on machine \#1,
  only 16 show some difference in pixels.
And on further inspection, the differences that do remain are indistinguishable
  to the human eye.
We attribute this to anti-aliasing.
Anti-aliasing is a technique used to smooth out jagged, slanted or curved lines
  that cross over pixels by blending them to make them smooth.
Anti-aliassing is necessary to draw smooth curves so that they are do not seem
  jarring to the human eyes.
To do anti-aliasing, you need to assume the geometries you are drawing ar
  real-avlaued constrains.
Our semantics do not admit that as we assume geometries to be a distinct
  collection of points.
Nevertheless, differences produced by anti-aliassing issues do not seem
  to be distinguishable by the human eye.
We show one such example in \Cref{fig:diff}.

\subsection{RQ2 Does the otpimnizer improve the render time of real world Skia
  programs?}

To answer this research question,
  we benchmark the rendering time of both the unoptimized and optimized
  \texttt{skp}s of the websites we discussed before.
To measure render time,
  we use \texttt{nanobench}, a benchmarking tool internal to Skia.
\texttt{nanobench} actually has many different benchmarking options,
  the \texttt{skp} \texttt{playback} options are what we use
  to measure render time.
As rendering time is not many magnitudes greater than the timer overhead%
\footnote{\texttt{nanobench} uses \texttt{std::chrono::steady\_clock} as its
  timer.}
  we need to choose a careful ebcnhmarking scheme that is able to factor out
  timer overhead.
We now describe how \texttt{nanobench} avoids that, by talking about the
  measurement scheme.
Before actually measuring the time taken to render for a specific \texttt{skp}
  file, \texttt{nanobench} first measures the number of loops of rendering
  needed to make the timing overhead negligible.
In \texttt{nanobench}, each reported sample is computed as:
  total elapsed time for a run, divided by the number of playback loops in that
  run.
So the key to making the timer overhead neglibible is to choose a good loop
  count.
For GPU playback, \texttt{nanobench}
  calculates the number of loops needed so each sample lasts about a target
  duration (default \texttt{--gpuMs=5} ms):
it doubles loops until the sample exceeds the target, then rescales loops to
  land near that target.
This makes each sample long enough that timer-call overhead is negligible.
Using this scheme, we measure 100 samples for each benchmark, both the optimized
  and unoptimized \texttt{skp}.
We summarize the rendering speedup across 100 samples using their geometric
  mean.
For this research question we only measure rendering time of all benchmarks
  on Machine \#1 running Skia's Graphite/Metal GPU backend.
Graphite is Skia’s new GPU rasterization backend, rebuilt for modern
  graphics APIs (like Metal, Vulkan, and D3D12) with a cleaner architecture and
  multithreaded rendering workflow.
Skia's older GPU backend, Ganesh, targeted GPU's through GL.

  in \foo we also show our optimizer's performance on Ganesh as well as other

\subsection{RQ2 Does the optimizer pay for itself}

While our optimizer does speed-up the rendering time large, high traffic
  websites, this rendering time is meaningless if the time taken to optimize
  is slow.
In this section we aim to show that our optimizer pays for itself i.e. the time
  to optimize a \texttt{skp} is always far smaller than the time taken to render
  the optimized \texttt{skp}.
To measure optimziation time, we replicated \texttt{nanobench}'s benchmarking
  scheme we described in \foo.

We first show optimization times in seperation to everrything else.
  \Cref{fig:grmetal-optscatter} is a scatter plot of the time taken to optimize

There arer two important facts to note from the figure.
First, like we claim in \Cref{sec:compiler},
  the time taken to optimize is linear wrt to the size of the Skia program.
Firthermore,

  commands in the Skia program, and that the time taken to optimization is far
  smaller than the time taken to render.
