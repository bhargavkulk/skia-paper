\section{Rewrites in \muskia}
\label{sec:rewrites}

This section provides a number of case studies,
  using the \muskia semantics to prove
  equivalences between \muskia programs.
It demonstrates that the \muskia semantics
  are sufficiently powerful to define and prove
  valuable optimizations on real-world Skia programs.
Specifically, we collected the Skia programs
  used by Google Chrome \fillin{\chromever}
  to render the top 100 websites
  and examined them to find common, suboptimal patterns.
In general, the suboptimality comes from
  using more \SaveLayer commands then necessary,
  and thus both using more GPU memory
  and also performing more blends
  than would otherwise be required.
To demonstrate the flexibility of the \muskia semantics,
  this section shows both general-purpose rewrites
  that apply to a vast range of Skia programs
  as well as more specific rewrites that we expect to apply
  only to Skia programs produced by Google Chrome
  or only to specific web frameworks or even websites.

It is important to understand what we mean by equivalence of \muskia programs.
The equality we will use in this section is always over entire programs.
We consider two \muskia programs to be equal
  when they evaluate to the same \Image under the semantics in
  \Cref{sec:semantics}.
We evaluate \muskia programs by first converting the \muskia program into \Layer
  terms as described by the operational semantics in \Cref{subsec:muskia}.
We then evaluate the \Layer terms into \Image{}s with the denotational semantics
  defined in \Cref{subsec:sem-layers}.
In this section, for every rewrite, we will present the rewrite as \muskia
  programs, then \Layer terms, and finally the core of the rewrite as an equality
  over the abstract model.
Throughout to section,
  we will group segments of possible \muskia commands with the notation
  ``$\ell\ldots$''.
We will use $\ell$ to refer to both the \muskia commands, and the \Layer term
  they all evaluate to.

\subsection{SrcOver \SaveLayer{}s}
\label{subsec:src-over-layer}

\SrcOver is by far the most common blend mode,
  corresponding to the normal intuitive meaning of
  ``drawing over'' some other image,
  and \SaveLayer{}s with \SrcOver blend mode
  are often unnecessary,
  suggesting the following idealized equivalence:
\begin{center}
  \begin{tabular}{S c S}
    \begin{tabular}{@{}l@{}}
      $\ell_1\ldots$ \\
      SaveLayer($p$ \{ \SrcOver \}); \\
      \quad $\ell_2\ldots$ \\
      Restore(); \\
      $\ell_3\ldots$
    \end{tabular}
    & = &
    \begin{tabular}{@{}l@{}}
      $\ell_1\ldots$ \\
      Save(); \\
      \quad $\ell_2\ldots$ \\
      Restore(); \\
      $\ell_3\ldots$
    \end{tabular}
  \end{tabular}
\end{center}
\noindent
Specifically, this equivalence holds
  when the commands labeled $\ell_2$
  all use \SrcOver blend mode.%
\footnote{If we also include opacity, then we must also restrict the savelayer
  to be opaque. We have formalized this restriction in our mechanization.}
Note that this equivalence replaces
  the \SaveLayer command
  by an equivalent \Save command
  instead of removing it entirely.
This is necessary to allow
  commands in $\ell_2$ to change the canvas state.
\Save is much cheaper to execute than \SaveLayer,
  since it does not require allocating a new GPU surface,
  so this equivalence still, in practice,
  significantly cuts computation time.

This equivalence is proven by induction
  over commands in $\ell_2$.
It is convenient to assume
  that sequential composition is left-associated
  (we do this in our Lean formalization)
This means the induction effectively proceeds by
  ``peeling off'' the last drawing command in $\ell_2$.
After expanding out the \muskia semantics,
  the inductive step requires proving
  the following equivalence of \Layer terms:

\begin{center}
  \begin{tabular}{S c S}
    \begin{tabular}{@{}l@{}}
      BlendLayer($\ell$\textsubscript{1}, \\
      \quad Draw($\ell$\textsubscript{2}, $g$, $p_d$ \{ \SrcOver \}, $c$), \\
      $p$)
    \end{tabular}
    & = &
    \begin{tabular}{@{}l@{}}
      Draw(BlendLayer($\ell$\textsubscript{1}, $\ell$\textsubscript{2}, $p_d$),\\
      \quad $g$, $p$, $c$)
    \end{tabular}
  \end{tabular}
\end{center}

Note the \Draw command uses a \SrcOver blend;
  this is why the commands in $\ell_2$
  must all use \SrcOver blends.
Applying this rewrite once ``peels'' a single \Draw command
  out of the inner \SaveLayer.
Applying it repeatedly results in the original equivalence
  of \muskia programs.

This equivalence is, in turn,
  equivalent to the following equality in our abstract model,
  which asserts that \SrcOver blends are associative:

\begin{equation*}
  \SrcOver(a, \SrcOver(b, c)) = \SrcOver(\SrcOver(a, b), c)
\end{equation*}

In our Lean formalization,
  we provide an instantiation of our abstract model
  using real-valued coordinates and real-valued colors,
  and prove this equivalence
  (including in the case of partial transparency).
There is also a base case to the recursion,
  involving a \BlendLayer of an \Empty layer.
One could optionally prove the case
  of a \BlendLayer of a \BlendLayer,
  but we did not see such Skia programs generated by Chrome.

\subsection{Dstin to Clip}

Another common blend mode is \dstin,
  which is used for masking.
While \dstin blend mode is important
  for handling complex blend shapes
  which are best constructed by
  a sequence of Skia drawing commands,
  they are inefficient for simple clip shapes.
Blending a full mask image with \dstin
  requires first filling all the pixels in the drawn shape,
  and then \dstin blending all pixels in the layer.
A \Clip operation, by contrast,
  only fills pixel inside
  both the drawn shape and the clip mask,
  and does not need to perform any follow-up blending at all.
This suggests the following idealized equivalence:

\begin{center}
  \begin{tabular}{S c S}
    \begin{tabular}{@{}l@{}}
      $\ell_1\ldots$ \\
      SaveLayer($p_1$ \{ \DstIn \}); \\
      \quad $\ell_2\ldots$ \\
      \quad Draw($g$, $p_2$ \{ \textsf{Solid}($c_2$), \SrcOver \}); \\
      Restore()
    \end{tabular}
    & = &
    \begin{tabular}{@{}l@{}}
      Clip($g$); \\
      $\ell_2\ldots$ \\
      $\ell_1\dots$ \\
    \end{tabular}
  \end{tabular}
\end{center}
In this case, the segment of \muskia commands labeled $\ell_1$
  is assumed to not contain \SaveLayer operations.
More importantly, $\ell_2$ \emph{has} to only contain \Clip commands.
This is because,
  we are only dealing with masks that are drawn with only one geometry,
  else we would also have to reason about the blend interactions of the various
  \Draw commands within the \DstIn \SaveLayer.
And as we are dealing with simple masks we want to turn into clips,
  we take the fill to be a \textsf{Solid} fill of an opaque \Color,
  noted in the example as $c_2$.

A challenge with verifying this rewrite
  is that it involves applying the \Clip operation
  to all operations in the segment labeled $\ell$.
To do so, we define a recursive function \textsf{clipAll}
  on \Layer terms:

\begin{align*}
  &\mathsf{clipAll} : \Layer \to \Shape \to \Layer \\
  &\mathsf{clipAll}(\Empty(), m) = \Empty() \\
  &\mathsf{clipAll}(\Draw(\ell, g, p, c), m)
                   = \Draw(\mathsf{clipAll}(\ell, m), g, p, c \cap m)
\end{align*}

Note that \textsf{clipAll} is not defined
  on \BlendLayer{}s,
  which do not have a clip mask parameter;
  this is why we must assume that $\ell$ does not contain
  any \SaveLayer{}s.
We then prove, by induction,
  that commuting \Clip over $\ell$ results in $\mathsf{clipAll}(\ell)$.

With this induction proven,
  the core \Layer equivalence becomes:

\begin{equation*}
\BlendLayer(\ell, \Draw(\Empty(), m, p_2, c), p_1) = \mathsf{clipAll}(\ell, c \cap m)
\end{equation*}

This is then proven by induction over $\ell$,
  recalling that it since $\ell$ contains no \SaveLayer commands,
  its denotation will contain no \BlendLayer{}s.
The base case, where $\ell$ is \Empty, is trivial,
  while the inductive case reduces to the following
  in the abstract model:
\begin{equation*}
\dstin\!\left(
\left\{
\begin{array}{ll}
  c_1, & x \in g \\
  \mathsf{Transparent}, & \text{otherwise}
\end{array}
\right\},
\left\{
\begin{array}{ll}
  c_2, & x \in c \cap m \\
  \mathsf{Transparent}, & \text{otherwise}
\end{array}
\right\}
\right)
=
\left\{
\begin{array}{ll}
  c_1, & x \in g \cap c \cap m \\
  \mathsf{Transparent}, & \text{otherwise}
\end{array}
\right\}
\end{equation*}
  where $c_2$ is known to be opaque.
This is proven by case analysis on $x \in g$ and $x \in c \cap m$.

While the high-level rewrite is straightforward,
  we initially wrote down an incorrect version
  of the high-level theorem,
  missing critical assumptions about
  the lack of \SaveLayer operations in $\ell$,
  the opacity of the colors involved, and the use of the \DstIn blend mode
  to draw the mask.
The proof with the \muskia semantics
  was critical to surfacing the need for these assumptions
  and ensuring that the rewrite was defined properly.

\subsection{Subsuming Filters}
\label{subsec:subsume-filters}

\begin{figure}
  \centering
  \begin{minipage}[c]{0.62\linewidth}
\begin{BVerbatim}[fontsize=\scriptsize]
<svg width="80" height="30" viewBox="0 0 80 30">
  <defs>
    <radialGradient id="b" ...>...</radialGradient>
    ...
    <pattern id="x" ...>
      <rect width="100" height="100" fill="#7D2AE7"/>
      ...
    </pattern>
  </defs>
  <mask id="a" ...>
    <path fill="#fff" d="M79.444 18.096 ... 69.192 21.888z"/>
  </mask>
  <rect mask="url(#a)" width="100" height="100" fill="url(#x)"/>
</svg>
\end{BVerbatim}
  \end{minipage}\hfill
  \begin{minipage}[c]{0.25\linewidth}
    \centering
    \frame{\includegraphics[width=\linewidth]{canva.pdf}}
  \end{minipage}
  \caption{SVG snippet used in this subsection, shown alongside its rendered result.}
  \label{fig:subsume-svg}
\end{figure}

SVG is a declarative, XML-based language for vector graphics.
It is, in other words, somewhat similar to SVG in purpose;
  browser engines like Chrome's translate SVG
  to Skia commands for rasterization.
\Cref{fig:subsume-svg}, for example,
  shows a snippet of SVG code from the Canva website.%
\footnote{
It is delightfully recursive
  that Canva is itself an online vector graphics tool,
  thought this snippet comes from the main page,
  not the main Canva editing UI.
}
In this snippet, the \texttt{<rect>} line draws a rectangle,
  but that rectangle uses a custom fill
  (the \texttt{<radialGradient>} defined in a \texttt{<defs>} block)
  and a custom mask (defined by a \texttt{<mask>} block)
  so that the Canva logo is ultimately drawn,
  which might strike the reader as quite similar
  to the \muskia semantics.

However, SVG and Skia differ enough
  that the conversion is not straightforward.
Chrome, for example, performs the fill-and-mask operation
  by drawing the mask on a \SaveLayer and blending it on the fill using \DstIn
  blending.
Moreover, as we discussed in \Cref{subsubsec:masking},
  \DstIn masks using the transparency of the mask layer,
  but in SVG (by default) masking is done by luminance,
  requiring an extra conversion step.
Chrome performs this conversion using
  a separate \SaveLayer with
  a luminance color filter.
The generated Skia program thus looks like this:

\begin{center}
  \begin{tabular}{S c S}
    \begin{tabular}{@{}l@{}}
      $\ell\ldots$ \\
      SaveLayer($p$ \{ SrcOver \}); \\
      \quad SaveLayer($p_1$ \{ \textsf{Luma}, \SrcOver \}); \\
      \quad \quad Draw(\textrm{\textit{mask}}, \\
      \quad \quad \quad \quad \quad $p_2$ \{ \textsf{Solid}(White), \SrcOver \}); \\
      \quad Restore() \\
      Restore()
    \end{tabular}
    & =
    & \begin{tabular}{@{}l@{}}
      $\ell\ldots$ \\
      SaveLayer($p$); \\
      \quad Draw(\textrm{\textit{mask}}, \\
      \quad \quad \quad \quad $p_3$ \{ Solid(Black), \SrcOver \}); \\
      Restore()
      \end{tabular}
  \end{tabular}
\end{center}

The equivalent Skia program on the right
  removes the \SaveLayer that performs the luminance conversion
  by simply applying luminance directly
  to the \Draw command's fill color.
Rewrites like the \DstIn to \Clip rewrite above
  can then further remove the \DstIn \SaveLayer.

Proving this rewrite in the \muskia semantics
  does not even require induction
  because it involves a fixed sequence of three Skia commands.
The core abstract model equation is:

\begin{equation*}
\Luma(\srcover(\Transparent, c)) = \srcover(\Transparent, \Luma(c))
\end{equation*}

The equation is trivially true
  because $\SrcOver(\Transparent, c) = c$.
Note that the analogous rewrite is not true
  when there are two \Draw commands
  inside the luminance filter \SaveLayer.
This is because this more general equation is not true:

\begin{equation*}
\Luma(\srcover(c_1, c_2)) \ne \srcover(\Luma(c_1), \Luma(c_2))
\end{equation*}

This again demonstrates the subtleties of 2D graphics optimizations
  and the need for the rigorous formal model
  provided by \muskia.

\subsection{Gradient Masks}
\label{subsec:grad-masks}

Finally, an extremely specialized rewrite
  concerns the use of gradients as masks
  as is common on Russian websites
  like \texttt{mail.ru}, \texttt{dzen.ru}, and \texttt{yandex.ru}
  (which together received just over 5 billion visits/month in January 2026).
All three of these sites seem to use a common web framework
  that seems to result in Chrome generating
  the following suboptimal Skia code:

\begin{center}
  \begin{tabular}{S c S}
    \begin{tabular}{@{}l@{}}
      SaveLayer(...);\\
      \quad Draw($s$, $p_1$ \{ SrcOver \});\\
      \quad SaveLayer( \{ DstIn \});\\
      \quad \quad Draw($s$, $p_2$ \{ Gradient(), SrcOver \});\\
      \quad Restore();\\
      Restore();
    \end{tabular}
    & = &
    \begin{tabular}{@{}l@{}}
      SaveLayer(...); \\
      \quad Draw($s$, $p_1$); \\
      Restore();
    \end{tabular}
  \end{tabular}
\end{center}

\noindent
On the left hand side,
  a gradient is used to draw the mask image.
However, with \dstin blending,
  only the opacity (alpha) of the mask is used, not its color,
  and in many cases the entirety of the gradient is opaque.
As a result, the mask operation is entirely superfluous.
It is not clear to use why this pattern is used;
  possibly the gradient could be configured to be
  partially transparent but isn't on these websites.
 No induction is needed in this example,
  since only a fixed number of \muskia commands are present.
Converting to \Layer terms, this rewrite unfolds to:

\begin{center}
  \begin{tabular}{S c S}
    \begin{tabular}{@{}l@{}}
      BlendLayer(Draw(Empty(), \textit{shape}, $p_1$, $c$)\\
      \quad \quad Draw(Empty(), \textit{shape}, $p_2$, $c$)\\
      \quad \quad \{ DstIn \})
    \end{tabular}
    & = &
    \begin{tabular}{@{}l@{}}
      Draw(Empty(), \textit{shape}, $p_1$, $c$)
    \end{tabular}
  \end{tabular}
\end{center}

\noindent
This reduces to the following equation in the abstract model:

\[
\DstIn(\SrcOver(\Transparent, a), b) = \SrcOver(\Transparent, a)
\]

\noindent
  where $b$ is known to be opaque,
  which it is because all of the stops of the gradient
  are themselves opaque.%
\footnote{
For more complicated fills like images,
  we could pessimistically assume them to not be opaque.
In principle, more precise reasoning might be possible,
  such as reading the Graphics Control Extension block's
  Transparent Color Index for GIF-formatted images.
}
Our Lean formalization proves this formula correct
  for our real-valued instantiation of the abstract model.
This rewrite is quite specialized
  (to a single web framework popular in a single country).
Without the certainty provided by the \muskia formalization,
  developing an optimization based on this rewrite would be risky,
  since any mistakes could affect other websites.
With \muskia, however,
  developing website-specific optimizations is not risky
  and becomes a simple engineering question
  trading off rasterization time for compilation time.
We turn to that next.
